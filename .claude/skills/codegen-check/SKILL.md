# このドキュメントについて

> **実装結果（コード＋テスト）を自己レビューする際の規約と作業手順**を定める。

## このスキルについて

製造済みの実装について、以下を客観的に確認する。

- 実装内容が詳細設計（および基本設計）と矛盾していないこと
- 実装が実装規約（コーディング規約・実装共通規範）に適合していること
- テストの内容が十分であること（観点の網羅・境界値・異常系）

本スキルでは **実装の修正は行わない**。検出した事項は、想定される対処方法とセットでユーザーに通知し、対応の是非・方法はユーザーに委ねる。

以下にこのスキルの動作プロセスを記載する。

### 1. レビュー対象と正本の準備

レビュー対象の実装コードとテストコードを特定する。引数で機能・定義書が指定されない場合は、対象範囲をユーザーに確認する。

比較対象となる正本の設計書は、**読む時に doctool を経由して最新化して読む**。バイナリ（詳細設計・基本設計 の docx/xlsx）は `doctool cache <src>`（未変更ならスキップ）を通してから `.doctool-cache/<相対パス>.md` を読む。**`.doctool-cache/` の .md を doctool を通さず直接読まない**（最新性を担保するため）。md／テキストは原本を直接読む。実装規約はリポジトリ内の正本を参照する（所在が不明な場合はユーザーに確認する）。

このとき `_old` や `bak` などのディレクトリ配下または zip ファイルにある旧バージョンは対象外とする。

**上流変更の検出**：`.codegen/sources.lock.json` に対象の記録があれば、記録された設計書の指紋を、同 lock に対する `doctool status --lock`（changed/missing があれば変更あり・終了コード1）で突き合わせ、前回実装時から上流（詳細設計・基本設計）が変わっていれば「実装が依拠した設計から上流が変わっている（再実装の要否確認）」を検出事項として報告する。詳細設計だけ変わり基本設計が未修正なら、基本設計⇔詳細設計のドリフトも差異として上げる（是正は docgen／人手であり本スキルでは行わない）。

### 2. 自己レビューの進め方

以下の順で、矛盾・不足がないことを確認する。

1. **詳細設計との整合**：実装の条件・分岐・計算規則・入出力変換・並び・ページング・異常系が、詳細設計の論理どおりに実装されているか。設計に無い挙動が足されていないか。
2. **基本設計との整合**：詳細設計を介して、システムとして実現すべき仕様から逸脱していないか。
3. **実装規約への適合**：命名規約・レイヤ責務・共通部品の所在・例外処理の様式に適合しているか。共有要素を重複実装していないか（DRY）。
4. **テストの十分性**：正常系・境界値・異常系が網羅され、詳細設計が定める分岐・判定基準を検証しているか。設計に無い挙動を固定化していないか。
5. **ビルド/テスト/フォーマッタ/リンタの状態**：通過状態を確認する（必要に応じ実行）。

### 3. 検出事項の扱い

内容に矛盾・不足があった場合は、それを書き留めて、想定される対処方法とセットでユーザーに通知する。

- 各指摘には**根拠（正本の出典：ファイル名＋位置、および実装の該当箇所：ファイルパス＋行）**を必ず添える。
- 「事実（正本と実装の差分）」と「解釈（こうすべきという推測）」を区別して報告する。
- このとき実際の対応（実装の修正）は行わず、対応の方法や実施の是非はユーザーに委ねる。
