# このドキュメントについて

> **同一の設計書体系・同一の開発方式を採るプロジェクト間で共通利用できる**、詳細設計書作成の **方法論・原則** を定める。
> **詳細設計書を作成・更新する際の規約と作業手順**を定める。
> 引数に作成する機能の指示がない場合はdocgen-planの全体計画における推奨する順序をなぞり、未着手の１工程を実施する。
> １工程づつユーザーに承認を受けて実行する。

## 記号の表記規約
本書では2種類のプレースホルダを使い分ける。
- `{{X}}` … **プロジェクトで一度決める固有値**。リポジトリ上のドキュメントに記載がなく判断出来ない場合は確認する。
- `<X>` … **成果物ごとに毎回埋める変数**。作成する設計書の対象に応じて埋める（例: `<物理名>`）。

## このスキルについて

- docgen-planにより策定された詳細設計の作成計画に基づき動作する。
  - docgen-planが実行されていない、最新化されていない場合は独立した別のエージェントでこれの実行を先行させる。
- テンプレートや凡例の設計書を利用して当該の機能の詳細設計を作成する。
- 型・サービス・テーブルは複数機能で共有される。**既に作成済みなら再利用し、重複作成しない**（変更があれば編集する）。
- 一覧表はシステム全体で1つの**索引**。個別定義書を作成・更新したら、対応する一覧表へ該当行を追加・更新する（未作成なら新規作成）。
- **進捗・決定台帳 `.docgen/progress.md` を着手前に読み（次の未着手工程の特定・「決定ログ」の踏襲）、工程完了後に更新する**（後述 §4）。台帳が無い場合は docgen-plan の実行を促す。

## 記載粒度の原則
詳細設計は原則として「**実装者が解釈のブレなく内容を実装できる**」粒度で書く。
これを満たさない記述（概要・要約止まり）は不可とする。
- **概要で済ませない**：「〜を適用して取得する」のような要約は不可。制御条件・分岐・繰り返し・対応関係・計算規則を、曖昧さなく定義する。
- **実装手段に依存しない**： 実際のプログラムを設計書中に記載しない。論理構造を記載する。
    - SQL文、`LIMIT`/`OFFSET`、`LIKE`、言語固有のメソッド名・型名 等は書かない。
- **曖昧さを残さない**（書くべき要素）：
  - 抽出/検索条件 … 対象項目・照合規則（完全一致/部分一致/範囲 等）・複数条件の結合（かつ/または）・未指定時の扱い
  - 並び替え … 並び替えキーと対象項目の対応・昇順/降順・既定の並び順・同値時/欠損時の扱い
  - ページング/件数 … 1ページ件数の定義・「何件目から何件」を求める計算規則・総件数の定義
  - 入出力/変換 … 入力項目と出力項目・テーブル列の対応関係と変換規則（書式・既定値・NULL/未設定の扱い）
  - 分岐/異常 … 条件ごとの結果・正常/異常の判定基準と分岐先
- **凡例は枠であって内容の見本ではない**：凡例のサンプルは様式（項目・表構成）を示すもの。サンプルの概要レベルをそのまま埋めない。
- **重複を書かない**：列見出しや他列が既に担う情報をセルで繰り返さない。各列にはその役割に固有の値のみを記す。
- **セルフチェック**：複数の実装者が読んで**同じ実装に収束するか**。分岐の余地が残るなら粒度不足。

記述の良し悪し（例）:
| × 不可（概要止まり / 実装依存）                | ○ 可（実装非依存・ブレなし）                                                                                                                             |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 検索条件・ソート・ページングを適用して取得する | 条件・並び・件数を下記のように規則として個別に定義する                                                                                                   |
| `status IN (:status)` で絞る                   | ステータス: 入力値のいずれかに一致する案件を対象とする。未指定時は既定の区分に一致する案件を対象とする                                                   |
| `title LIKE '%:title%'`                        | 件名: 入力値を部分一致（前後任意）で照合する。未入力なら条件に含めない                                                                                   |
| `ORDER BY id DESC`                             | 並び順: 並び替えキーに対応する項目で昇順/降順に整列する。未指定時は既定キーの降順とする                                                                  |
| `LIMIT :n OFFSET (:p-1)*:n`                    | ページング: 1ページの件数を pageSize とし、(ページ番号−1)×pageSize 件を読み飛ばした次から pageSize 件を取得する。pageSize が「全件」なら全件を対象とする |

## 1. 入力と成果物

docgen-planにおいて作成した計画(プロジェクトルートの`.docgen/plan/` 配下)を参考にする。
およそ以下のような内容に収まるはずである。

- 入力
  - 基本設計書（機能仕様書・画面レイアウト・エンティティ定義書・システム共通仕様書・開発基底定義 等）
  - 雛形（凡例）: 同階層 `凡例/`（各様式の**様式構成の正本**）
  - 凡例に対する各ドキュメント書式について記載ルールなどの説明資料
  - 進捗・決定台帳 `.docgen/progress.md`（docgen-plan が初期化。次の未着手工程・横断的決定の参照元）
- 成果物: 詳細設計書。対応する凡例と同一のレイアウト・表構成・記法で作成する（**配置は §1.1 に従う**）。

### 1.1 成果物の配置（機能グループ別フォルダ）

各定義書の出力先は、その**機能グループ**に応じてサブフォルダへ分類する。配置は凡例ツリーのミラーでは決めず（凡例は様式ごとに1つ＝フラットであり、配置の根拠にはしない）、本規則で明示的に決める。

- **機能グループに帰属する定義書**（イベント定義書配下＝コントローラー定義書・サービス定義書・画面イベント定義書）は `<種別フォルダ>/<連番_機能グループ>/<ファイル名>` に置く。
  - 機能グループは各定義書ヘッダーの「機能グループ」欄の値（§2 で転記する値）と一致させる。ヘッダー値から一意に定まり、別途の判断を要しない。
  - フォルダ名の**連番接頭辞**は、プロジェクト固有の「機能グループ→連番 対応表」（`.docgen/plan/全体計画.md` に定義し、進捗台帳 `.docgen/progress.md` の決定ログにも記録）に従う。
- **さらに細分する種別（画面単位）**: 1つの機能グループ内で細分単位（画面等）ごとに多数の定義書が生じる種別は、機能グループフォルダの下にさらに細分サブフォルダを設ける。**画面イベント定義書**は `画面イベント定義書/<連番_機能グループ>/<連番_画面>/<ファイル名>` とし、画面はヘッダー機能欄「`<画面> / <イベント>`」の画面部分（＝ファイル名先頭セグメント）で一意に定まる。細分の採番もプロジェクト固有の「画面→連番 対応表」（全体計画）に従う。コントローラー定義書・サービス定義書はこの細分を行わず、機能グループ階層のままとする。
- **複数機能で共有される定義書**（型情報・テーブル・DBIF 等、単一の機能グループに属さないもの）は機能グループ分けせず、各種別フォルダ直下に置く。
- **索引（一覧表）**はシステム全体で各1のため、機能グループのサブフォルダには入れず、対応する種別フォルダの親階層（従来位置）に置く。
- **既存定義書の更新時**は、当該機能グループのサブフォルダ内（無ければ種別フォルダ配下）を探索して既存ファイルを特定し、フラット位置に重複生成しない。

## 2. ドキュメントの書き起こしの方法
凡例をコピーし、本文・ヘッダーのセルを差し替えて生成する（ゼロから新規生成しない＝レイアウト・罫線・書式を完全継承）。
読み取り・解析・生成にはツール **doctool** を用いる

**生成前に雛形を解析して記入ストラテジを決める（決め打ち禁止）。**
雛形により欄の仕様が異なるため、固定の前提（「No列は空」等）を置かず、`doctool analyze` で各欄の性質を判定して記入方法を選ぶ：
- **列の役割（内容を埋める前に決める）**：各列が担う情報を見出しから判定し、それ以外を書かない。
- **採番欄（No列等）**：自動採番（`w:numPr`）あり→値を入れない（Wordが採番。`fillTable` に `null` を渡す。値を渡すと警告の上スキップされる）。なし→連番を記入。**1列内で手打ち連番と自動採番を混在させない**。
  - **表ごとに独立採番（表をまたいで連番継続しない）**：自動採番は `numId` 単位で1つの連番カウンタを共有するため、同一文書に採番表が複数あると（複製や凡例の `numId` 共有により）表をまたいで連番が地続きになる。各表が1始まりで振り直されるよう、`doctool fill` は保存前に採番を自動正規化する（表ごとに別 `numId` を割当て）。**段落の直接 `numPr` だけでなく、段落スタイル由来（heading 等）の連番も対象**（スタイル採番の表には直接 `numPr` を被せて独立させる）。手動編集等で既存ファイルに地続きが残る場合は `doctool normalize <file>` で是正する。
- **ページ欄・日付・作成者**：`PAGE`/`NUMPAGES`/`DATE` 等のフィールドあり→触らない。固定テキストなら値を設定。
- **セル構造**：結合セル（被覆側へは記入不可。起点セルへ記入）、複数段落セル（機能セル等。`paragraphs` で段落ごとに値を指定）を判定して記入位置を決める。
- 解析で判定できない特殊構造（テキストボックス・特殊フィールド・ネストテーブル等）は、推測で埋めず**ユーザーに確認**する。

記入の実務：
- `doctool dump` で雛形の IR を読み、差し替え対象の座標（part / block / row / col）を特定して記入スペック（`setCell` / `setParagraph` / `deleteBlock` / `fillTable`）を作成し、`doctool fill` で生成する。
- **ヘッダー枠**：機能グループ・機能セル（カテゴリ＋具体名）・作成年月日・作成者を差し替える。**機能グループは対象機能の基本設計ヘッダー「機能グループ」欄から転記する**（グループ無しは `―`）。機能セルは様式により **2段落（改行区切り）か1段落（全角スペース区切り）** で構造が異なるため、`analyze` の段落数判定に従う。
- **基本情報表**：ラベル行の値セルを差し替える。
- **明細表（行可変）**：`fillTable` が凡例の**データ行を複製**して必要行数に増減し、各セルを設定する（行の罫線・書式を継承）。
- **凡例の不整合は成果物側で正す**：列見出しの誤記、一覧表のヘッダー文書種別の取り残し、流用された様式 等。

## 3. 凡例利用上の原則
- 凡例には **サンプル値・他様式からの流用の取り残し・誤記**が含まれることがある。成果物では正す。
- **各様式の正しい構成は、その様式自身の凡例を正**とする。流用が疑われる場合は元様式の凡例と突き合わせる。
- **凡例サンプル中の物理 DB 型は例示のダイアレクト**であり、成果物はシステム構成で規定する DB 製品のダイアレクトに従う。凡例の型名をそのまま転記しない。
- **一覧表のサンプル行は転記しない**：一覧表の成果物は、実在する個別定義書とのみ 1:1 で対応させる。凡例のサンプル行（実在しない機能の例示を含む）を成果物に引き継がない。

## 4. 作業の進め方

> **生成の承認ゲート（最優先・厳守）**: `doctool fill` による生成は、**直前のユーザー発言に明示の生成許可**（例:「生成OK」「作成して」）がある時のみ実行する。**部分的な修正指示・質問への回答・沈黙を「残りの暗黙承認」と解釈して生成に進んではならない**。修正指示を受けたら、その反映後に改めて明示の許可を求める。判断に迷う場合は生成せず確認する。

1. **着手時に `.docgen/progress.md` を読む**：引数で機能が指定されない場合は工程進捗から**次の未着手工程**を選ぶ。あわせて「決定ログ」を読み、命名・方針を踏襲する（表記ゆれ・再導出を防ぐ）。**あわせて変更検出（reconciliation）**：`.docgen/sources.lock.json` に対象の記録があれば、記録された基本設計の指紋を、同 lock に対する `doctool status --lock`（changed/missing があれば変更あり・終了コード1）で突き合わせ、前回作成時から基本設計が変わっていれば影響する詳細設計を洗い出して本工程に取り込む。
2. 作成前に計画を立て、方針・影響範囲・リスクを説明して合意を得る。
3. 対象機能の基本設計書を読み（**doctool を経由して最新化して読む**。バイナリは `doctool cache` 経由・`.doctool-cache/` の .md を直接読まない、md／テキストは原本直読み）、優先度に従い各個別定義書と対応する一覧表を、凡例を雛形として作成・更新する。
4. 作成後、凡例とのレイアウト・項目差分を**目視確認**する。
5. 続けて 後述の**自己確認**を行い、全観点を満たすことを確認してから完了とする。
6. **完了時に `.docgen/progress.md` を更新する**：当該工程を `- [x]` に変え、成果物パスを記録し、本工程で生じた横断的決定・技術メモ・申し送りを各セクションへ追記する。台帳更新は生成後の事実記録であり承認ゲートの対象外（生成自体は明示許可時のみ）。あわせて、当該工程で消費した基本設計（primary）の指紋を `.docgen/sources.lock.json` に記録する（`doctool hash`。次回の変更検出ベースライン）。
7. 判断に迷う点・凡例に無い事項は、勝手に決めずユーザーに確認する。
8. 個人情報・認証情報・シークレットは設計書・ログに残さない。

### 4.1 自己確認（生成物の正本整合チェック）
生成は対象（機能・様式）ごとに変数を埋める作業であり、変数の取り違え・正本に無い値の創作が混入しうる。
**生成後に成果物そのものを読み直し、正本（基本設計・各一覧表）と突き合わせて整合を確かめる**ことを完了条件とする。
満たさない点があれば、勝手に取り繕わず直す（直し方が不明なら勝手に決めずユーザーに確認する）。

**観点**
- **正本に無い値を創作しない**：成果物が指す機能・型・テーブル等は、**基本設計（および各一覧表）に実在するもの**だけを用いる。生成物の名称・分類を、対象の内容から推測して新造しない。
- **名称の自己整合**：成果物のファイル名・ヘッダー・本文で同一対象を指す表記は、互いに食い違わない。
- **索引との整合**：個別定義書とそれを束ねる一覧表（索引）が 1:1 で対応する（作成・更新したら索引へ反映済みである）。
- 生成された設計書を元にプログラムの実装が可能であること
- すべての物理名（型・プロパティ・クラス・メソッド・テーブル/列/制約・エンドポイント等）が命名規則に適合する識別子であること。
- 物理名欄に論理名・説明・値域などの自然言語を書いていないこと
- **冗長記述の排除**：各列について、列見出し・他列・統制語彙が既に担う情報をセル本文で重複していないか確認する。重複があれば項目固有の差分のみ残す。
- **採番の表ごと独立**：自動採番のNo列が、表ごとに1始まりで振り直されているか（表をまたいで連番が継続＝地続きになっていないか）を確認する。地続きがあれば `doctool normalize` で是正する。
