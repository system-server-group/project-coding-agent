# 詳細設計書 共通記載規範

> 本書は詳細設計書（全様式）に共通する記載規範を定める。各様式固有の規範は、本書群の各様式別の記載規範を参照。
> 様式の構成（項目・表・列・記法）の正本は各様式の凡例（`詳細設計/凡例/`）。本書はその記入方法・解釈を補う規範であり、様式そのものを再定義しない。
> 本書の例はすべて凡例ベースの抽象例（`Sample…` 等）であり、特定機能には依存しない。

## 正本の考え方
- **様式構成**の正本：各様式の凡例。
- **物理名の実体一覧**の正本：各「一覧表（索引）」設計書。
- **表構造（永続化レコード＝永続化エンティティ型 `～Entity`）**の正本：テーブル定義書。型情報に同一構造を二重定義しない。
- **ドメイン型**の正本：型情報定義書（モデル型／列挙型）。
- **型の日付/日時区別・区分値**の正本：基本設計のエンティティ定義書。
- **入力値チェック**の正本：基本設計のシステム共通仕様書（入力値チェック）。

## ヘッダー枠（全様式共通）
| 項目               | 規範                                                                                                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 文書種別名（左上） | 様式名。凡例のまま（誤記があれば成果物で正す）。                                                                                                                                                                                                 |
| システム：         | システム名（プロジェクト固定値）。                                                                                                                                                                                                               |
| 機能グループ：     | **機能固有の様式**（イベント・コントローラー・サービス・対象表のDB/IF 等）は対象機能の基本設計ヘッダー「機能グループ」を転記。**複数機能で共有・横断する様式**（型情報・テーブル・画面テンプレート、および各一覧表＝システム全体の索引）は `―`。 |
| 機能：             | 様式により単段落／2段落。凡例を `analyze` の段落数判定に従う。機能固有の個別定義書は「機能名／対象名」の**2段落**、横断型・索引は対象名の**単段落** が基本。                                                                                     |
| 作成年月日／作成者 | 作成日＝生成日（`YYYY-MM-DD`）。作成者＝生成時に明示された氏名のみ。基本設計・既存物・凡例からの**流用禁止**。                                                                                                                                   |
| 変更年月日／変更者 | 新規作成時は空。                                                                                                                                                                                                                                 |
| ページ             | `PAGE`/`NUMPAGES` フィールド。**触らない**。                                                                                                                                                                                                     |

## 命名規則（物理名）
- 型・型情報：PascalCase（例 `SampleType`）。
- 列挙型の定数：コード（例 `OPEN`）。値の型は文字列。
- プロパティ・メソッド・API入出力：camelCase（例 `sampleValue`）。
- クラス：サービス `～Service`／コントローラー `～Ctrl`／データアクセス `～Mapper`（PascalCase）。
- 永続化エンティティ：`～Entity`（テーブル物理名のPascalCase。テーブル名は複数形なので複数形由来。例 `projects`→`ProjectsEntity`）。構造の正本はテーブル定義書（型情報に二重定義しない）。
- エンドポイント：API＝`/api/<グループ>/<アクション>`、画面＝`/<パス>`（`/api` を付けない）。`/api/**`＝API（JSON）／それ以外＝画面（View）で種別判別。
- DB識別子（テーブル・列・制約/索引）：小文字スネークケース。
- **物理名欄に論理名・説明・値域などの自然言語を書かない**。

## 型語彙
- 基本型：型情報一覧表「基本型情報」を正本（`string`/`number`/`integer`/`boolean`/`date`/`datetime`/`file` 等）。繰り返しは `型[]`。
- モデル型（ドメイン／DTO）・列挙型：プロジェクト固有。型情報の各小表を正本。
- 物理DB型（テーブル定義書）：システム構成で指定したDB製品のダイアレクトで定義。**日付と日時を区別**。
- **区分（列挙型）を永続化する列は文字列コードで保持**（DBは `varchar` 等）。NULL可否はエンティティ定義書の必須欄に従う。

## 参照記法
- 他定義書・API・テーブル・型・画面を参照：`【名称】` で囲む。
- プロジェクト固有の型を参照：`※型定義書【...】を参照`。
- 表（永続化レコード＝永続化エンティティ型 `～Entity`）を参照：`※テーブル定義書【...】を参照`。
- 画面（テンプレート）を参照：`※画面テンプレート一覧【...】を参照`。

## 索引（一覧表）との整合
- 個別定義書を作成・更新したら、対応する一覧表（システム全体で1つの索引）へ反映。**個別↔索引は 1:1**。
- 凡例のサンプル行は転記しない（実在する個別定義書とのみ対応させる）。

## 記載粒度
- 実装者が解釈のブレなく実装できる粒度。概要・要約止まりは不可。
- **実装手段に依存しない論理的な制御条件**で書く（SQL文・`LIKE`/`LIMIT`、言語固有のメソッド名・型名を書かない）。
- 抽出条件・並び替え・ページング・入出力変換・分岐/異常を曖昧さなく定義（照合規則／結合（かつ・または）／未指定時の扱い／境界の包含 等）。
- 列見出し・他列・統制語彙が既に担う情報をセルで重複しない。

## 採番・セル構造
- 自動採番欄（`w:numPr` あり）：値を入れない。非採番のNo欄は様式に従う（凡例が空欄なら空欄）。1列内で手打ち連番と自動採番を混在させない。
- 結合セルは起点へ記入。複数段落セルは段落ごとに指定。
- フィールド（`PAGE`/`DATE` 等）は触らない。

## レイヤ責務・設計方針
- レイヤ：**画面/APIコントローラー → サービス → データアクセス（DB/IF Mapper）**。
- **業務ロジック**（検索条件の組立・絞り込み・ドメイン変換等）は**サービス層**に置く。コントローラーは入力チェックとサービス委譲に徹し、ロジックを重複詳細化しない。
- データアクセス（Mapper）は**1表専用**（他表を操作しない）。入出力は対象表のレコード（テーブル定義書を正本に参照）。サービスが**レコード⇄ドメイン型**を変換する。
- 画面の状態は**クライアント側のローカルストレージ**で管理し、状態保持のためのサーバAPI／セッションを派生させない。
- **横断参照データ（名称等のマスタ取得）はリソース指向で設計する**：複数機能から参照される名称・マスタの取得は、**対象（マスタ種別）ごと**にエンドポイント／サービスメソッド／DB/IF を定義し、**機能（ページ）単位でエンドポイントを増やさない**。コントローラー（API）・サービス・データアクセスを対象リソースで **1:1** に対応させ、参照側ごとに再生産しない。取得粒度は用途（オートコンプリート等）に限定し、レコード全体が必要な場合は当該マスタの管理 API を用いる。これらの様式の機能グループは**対象マスタの所属**（例：マスタ管理）とし、特定の参照元機能には紐付けない。

## 凡例の扱い
- 凡例にはサンプル値・他様式からの流用の取り残し・誤記が含まれることがある。成果物では正す（例：機能グループ欄のシステム名流用、節見出しラベルの取り違え、索引物理名の接尾辞誤記）。
- 各様式の正しい構成は、その様式自身の凡例を正とする。
