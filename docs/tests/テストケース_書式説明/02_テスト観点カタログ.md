# テスト観点カタログ

> 共通規範は [00_共通規範.md](00_共通規範.md)、様式は [01_テスト仕様書.md](01_テスト仕様書.md) を参照。

## 位置づけ

- 設計・実装から E2E テストケースを導出する際の**観点の網羅チェックリスト**であり、テスト仕様書の**セクション区分の標準候補**。
- **カタログは閉じた分類ではない**。網羅の担保は、テスト仕様の出典・ケースID・導出判断メモの対象外から check 時に再生成する連結（設計項目↔ケースの対応）が担い、カタログはその整理の標準を示すもの。**どの観点にも収まらない導出単位を対象外とする理由にカタログを用いない**。
- **機能固有の観点まとまり（例：添付ファイル・編集保護・テーブル操作）は、独立したセクションとして立ててよい**。複数の汎用観点に飛散するより、機能のかたまりで束ねた方が読みやすい場合はそちらを優先する。
- 該当ケースの無い観点セクションは設けない（空セクション・欠番を作らない）。
- 各観点の「導出元」は詳細設計を基準とし、基本設計は補完に用いる（testgen-plan の規定に従う）。

## 観点一覧（セクション候補）

### 1. 画面仕様・初期表示
- **導出元**: 画面イベント定義書（初期表示）、基本設計の画面レイアウト、画面テンプレート一覧
- **確認内容**: 表示項目・ラベル・プレースホルダ・既定値、初期状態（マスク表示・活性/非活性）、保存状態の復元、ロール別の表示差
- **期待結果の形**: 「◯◯が表示される／されない」という画面観測

### 2. 画面イベント処理（クライアント挙動）
- **導出元**: 画面イベント定義書（トグル・切替・テーブル操作・ファイル選択 等）
- **確認内容**: 押下・切替に対する画面内の状態変化（表示切替、行の展開、ソート・フィルタ・ページング、クライアント側の状態保存）
- **期待結果の形**: 遷移を伴わない画面内の変化

### 3. 画面遷移
- **導出元**: 画面遷移図、コントローラー定義書
- **確認内容**: ナビゲーション遷移、戻る、登録/更新後の遷移先、ログイン済みリダイレクト、直リンクアクセス
- **期待結果の形**: 遷移先URLと遷移後画面の識別要素

### 4. サーバー/APIサービス処理（正常系・異常系）
- **導出元**: サービス定義書、コントローラー定義書、シーケンス図、エラー画面定義書
- **確認内容**: 登録・更新・検索・削除が業務として成立し結果が画面に反映されること、メール送信等の副作用、および**処理の異常分岐**（DB例外→ロールバック・エラー画面、楽観排他失敗、存在しないIDの指定、404/403/500 のエラー画面表示）
- **期待結果の形**: 操作後に画面から観測できる反映（一覧に現れる・値が変わる・完了メッセージ）、異常時はエラー画面・エラーメッセージの内容と**副作用が起きていないこと**（ロールバック等）

### 5. 入力チェック
- **導出元**: モデル型定義書（Form）のサーバー側検証ルール、メッセージ定義
- **確認内容**: 必須・文字種・文字数・形式・相関（日付範囲等）・列挙値。**サーバー検証を軸**とし、期待結果はサーバー検証の観測（再表示・メッセージ・未登録）で書く。クライアント検証固有の挙動は【クライアント検証】タグ付きの補助観点とする
- **期待結果の形**: エラーメッセージの文言と表示位置＋否定の観測（他項目のエラーが出ない・登録されない・入力値の保持）

### 6. 認証・認可
- **導出元**: 認証・認可サービス定義書、コントローラー一覧表のロール制約
- **確認内容**: **各機能ではロール別の可否差分のみ**を書く（画面/APIのアクセス可否〔403〕・ロール別の表示差）。未認証アクセスの誘導・セッション失効・API未認証（401）など**共通の認証挙動は共通基盤機能（共通レイアウト・ログイン）側のテストが担い**、機能側で重複させない
- **期待結果の形**: 遷移先・HTTPステータス・表示差

### 7. 外部入出力（CSV・添付ファイル）
- **導出元**: 画面イベント定義書（CSVアップロード/ダウンロード・添付ファイル操作）、DBIF定義書
- **確認内容**: 出力内容の正しさ（列・件数・値・文字コード・エスケープ）、取込の反映（洗い替え/編集の別）と**取込エラー**（形式不正・列不足等）、ファイルの追加・削除
- **期待結果の形**: ダウンロード物の中身、取込後の一覧表示。参照テストデータ欄に正本csvパス必須
- **補足**: 添付ファイルのように選択チェック・永続化・ダウンロード/削除が一連となる場合は、汎用観点に分散させず**機能固有セクション（例：「添付ファイル」）として一塊で立てる**ことを推奨

## 横断原則

- 1ケース1観点。期待結果は画面から観測できる挙動で合否が一意に決まること。
- **境界値は独立セクションとしない**。該当する観点（入力チェック・ファイル選択・検索仕様 等）のケースとして設計し、正常/異常の該当側に分類のうえ観点欄に【境界値】と明記する（様式の規範に従う）。
- **データ整合・永続化は独立セクションとしない**。登録内容の反映・再表示後の保持・一意制約の扱いは、サービス処理ケースの**期待結果に内包**して画面から観測できる形で書く（E2E では DB を直接参照しない）。
- 到達不能な観点（画面制約で発生し得ない）は断定せず確認事項として提示する。
- 観点がどのセクションに属するか迷う場合は、**確認の主目的**（何が壊れたら失敗とするか）で分類し、複数セクションに重複させない。帰属先が無い場合は機能固有セクションを立てる。
