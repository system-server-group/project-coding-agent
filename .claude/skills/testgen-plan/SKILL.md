# 引数と対象の解決
- 第1引数（必須）: **実施単位**（テストディレクトリ名）。テストケース仕様ルート（解決は testgen-shared の実施単位・配置規範）直下の `<実施単位>/` を作業対象とする。未指定なら既定値を置かず、**停止してユーザーに確認**する（ハーネスの `-Pe2e.target` と同じ思想）。
- 第2引数以降: **機能名**（機能フォルダ名）。**省略時は全機能**（新規導出＝設計の画面一覧にある全機能＋横断仕様のオーナー機能／流用＝複製されている全機能）。絞りたい場合だけ指定する。機能名をユーザーに尋ねない。
- 第1引数のディレクトリが**存在しなければ新規導出**、**存在すれば既存内容への作業**（§0 で機械的に決まる。**ユーザーへ種別・流用元・複製の要否を尋ねない**）。指定された実施単位の中だけで作業する。

# 目的と境界
- 設計から観点・シナリオを導出し、**ケース本文・入力データ・期待値を一体で完成**させて、テストケース仕様書 `<機能>_テスト仕様書.xlsx` に**直接記入**する。
- 設計変更時は**影響範囲を特定し、該当箇所のみを更新**する（全再生成・一括削除はしない）。
- 期待結果は入力データの内容の関数であり、**データを確定せずに期待値は確定できない**。確定を後工程へ先送りしない。
- 担当境界：**plan＝ケース＋入力データ＋期待値を完成（再テスト等では人が複製した一式の検分・整備を含む）**／**testgen-exec＝完成物を入力に、テストコードの作成・実行（証跡取得を含む）**。plan は E2E コードの実装・実行をしない（例外：2回目以降の実施でケースを変更する際の、変更前確認のための実行のみ）。

# 前提
- **共有規範**: Skill ツールで `testgen-shared` を読み込み、その規範（文書正本規範・実施単位・配置規範・証跡規範・実行ハーネス規範・テストデータ規範）に従う。読み込めない場合は作業せず停止してユーザーに確認する。プロジェクト側に「テスト規約」ロールの上書き文書がある場合、プロジェクト固有の決定はそれが優先する。規範に無く判断できない事項はユーザーに確認する。
- **観点カタログ**（書式説明）をセクション構成の標準とする。書式凡例は書式の参照であり内容の正本ではない（書式説明・書式凡例は「テストケース様式」ロールとして解決する。文書正本規範参照）。

# 入力・成果物
- 入力：詳細設計（**導出の基準**）、基本設計（画面遷移・レイアウト・イベント／視覚はモックアップ。各設計文書は文書正本規範のロールとして解決し、正本の優先順位も同規範に従う）、**同じ実施単位の**既存テストケース仕様・E2E実装、変更履歴。既存仕様・E2E実装は**存在する場合のみ**の入力であり、**無いことは正常**（E2E実装は exec が後工程で作る）。
- 成果物：`<機能>_テスト仕様書.xlsx`（**単一正本**）、入力データ正本・期待値ファイル、導出判断メモ（非正本）、`sources.lock.json`・`spec.lock.json`（実施単位フォルダ直下）、`ケース変更台帳.md`（人手変更の裁定記録・非正本）、質問リスト・変更影響分析。

# 正本と所有権（不変条件）
- **正本は xlsx ただ一つ**。人の記入（受け入れ条件・実施結果）を保存したまま、doctool で現物を dump して**該当セルだけを更新**する。md 草案は持たない。
- 設計書は導出根拠であって正本ではない。**xlsx 更新の判断に git 状態を使わない**。
- 作業は指定された実施単位（第1引数）の中に閉じる。**過去の実施単位は読まない**（実施記録であって plan の入力ではない）。
- 導出判断メモは**生成時点の導出記録として凍結**する（§11 承認後は書き換えない）。承認後の人手変更の正史は `ケース変更台帳.md`（追記のみ・記帳はスキルが代行）が担い、網羅の再証明は「メモ ⊕ 変更台帳 ⊕ 現物 xlsx」の機械照合（§8）で行う。

# 記載規律
1. **操作手順は画面で観測可能な操作として書く**。「datalist を確認する」「属性を確認する」等の内部検査表現は禁止（例:「入力欄をクリックし候補を表示する」）。
2. **期待結果の各行に 可視／【機械検証】 の別を明記する**。画面から観測できない期待結果（属性・HTTP応答・不送信の否定観測・DL内容のバイト一致等）は行頭に**【機械検証】**を付け、なぜ画面で確認できないかを導出判断メモに残す。可視の期待結果は証跡のフレームで、【機械検証】は steps.json の実測値で受け入れる前提になる。
3. **具体IDの明示**: シード CSV は全行に主キーを持ち、期待結果には具体 ID（例 `/items/detail/1`・「ID: 1」）を書いて、画面表示と証跡上で突合できるようにする。
4. **1画面原則**: 検証対象が 1 フレームに収まるデータ量・表示件数でケースを設計する（ページング・スクロールが本質のケースは連続フレーム前提で設計し、行キーで連続性を確認できる期待値にする）。
5. 状態遷移（表示↔非表示・消去）のケースは、**変化前の状態確認を操作手順に含める**（証跡は前後フレームで取られる）。
6. **複数のUI要素が同一挙動をすることを主張する期待結果**（例: 上部・下部の「戻る」ボタン）は、代表1つの操作＋属性比較で済ませず、**各要素を実際に操作する**手順・期待結果にする。
7. **大量リストの内容一致**（オートコンプリート候補等）は、期待値を**正本CSV参照**とし、期待結果には「先頭数件の具体値＋全件は正本と【機械検証】で一致」と書く（全件の列挙・フレーム化はしない）。
8. **記録は宣言ではなく観測から書く**: 導出判断メモの突合記録・変更台帳・README 等の記録に書く統計・解消の記述は、整合チェッカー `report` の機械実測と突合報告（証拠ファイル）からの転記のみとする。「追補した」「是正した」「解消済み」は、該当の変更が現物に反映されていることを `check` の再実行で確認してから記す（意図・記憶からの記帳の禁止——データ事実表と同じ関所を記録にも適用する）。一括スクリプトで記録を書く場合も、統計・解消宣言を固定文字列として埋め込まない。

# 手順
## 0. 実施単位の解決とモード決定
モードは第1引数のディレクトリの状態から**機械的に**決まり、**確認事項ではない**。スキルの起動そのものが作業指示であり、決まったモードについて「どちらで進めるか」「流用の意図では」と尋ねること・懸念として提示することを**禁止**する。ユーザーに確認してよいのは **第1引数の欠落／規約に無く判断できない事項／§11 の承認ゲート** の3つだけ。
- 判定に使ってよい事実は**第1引数のディレクトリの状態だけ**。実施単位の名称・規約の流用複製の規定・過去の実施単位から起こし方を推測しない。**過去の実施単位（第1引数以外の実施単位フォルダ）は、目的を問わず開かない・読まない・集計しない**。
- 流用は「人がフォルダを複製済み」という事実でのみ表現される。本スキルは複製せず、流用を提案しない。
- **存在しない** → **新規導出**。フォルダを新設し、直下の `README.md` に「新規導出・対象機能」を記録して §1〜§11 を行う。機能名省略時は**設計の画面一覧にある全機能**が対象（尋ねない）。横断仕様のオーナー機能フォルダ（実施単位・配置規範の既定 `00_共通部品`）もこのとき新設する。
- **存在し `README.md` がある** → その記録（新規導出／流用・対象機能）に従い**続きから**作業する。
- **存在し `README.md` が無い** → 人が複製で用意した**流用一式**とみなし §R（検分）から行う。
- 再呼び出しや作業の分割で複製・一括再生成が再実行されることはない（更新は常にセル単位・該当箇所のみ）。
- 2回目以降の実施でケース変更が必要な場合、変更前に対象機能の E2E を実行し、期待と結果のずれがないことを確認する（ずれがあれば立ち止まる）。対象機能の E2E 実装がまだ無い場合、この確認は不要。

## R. 流用（人が複製した一式）の手順
人が実施単位フォルダを複製して用意した一式に対する再実施（複製の内容は規約「流用複製の規定」）。本スキルは複製を行わず、複製済み一式の**検分・整備と差分適用**だけを行う。新規導出（§1〜§8）は行わない。
1. **複製の検分**: 規約の規定に照らして確認する——`_baseline/data/`・仕様書 xlsx・`data/`・導出判断メモが揃っているか／**非複製物（エビデンス・受け入れ確認レポート・進捗台帳）の持ち込みが無いか**／対象機能の E2E 実装が**存在する場合に**検証部品ベース（`@EvidenceV2` 付与）であるか（方式の異なる証跡の混在防止。**実装が無いことは不適合ではない**——exec が後工程で作る）。不適合は勝手に直さず報告する。あわせて整合チェッカー `check --partial` を実行し（部分再テストでは対象外ケース除去による欠落・欠番を警告として扱う）、指摘を検分結果に含める。
2. **仕様書の整え**: 実施結果・実施日等の記入欄をクリアする。対象ケースのみの再テストは**対象外ケースを除いた仕様書**にする（ケース No は元の番号を維持）。全件再走行はそのまま。レイアウトは §10 と同じ基準で確認する。
3. **差分適用**: ケースの変更が必要な場合のみ §9（変更影響分析）→ §10（記入・レイアウト・lock）を該当箇所に適用する（複製元が記載規律に合っていない場合の是正もここで行う）。変更ゼロなら記入はしない。
4. **記録**: 実施単位フォルダ直下の `README.md` に**流用である旨と対象機能**を記録する（流用元が判る場合は併記。対象ケースを絞る部分再テストでは対象ケース範囲も記録する）。
5. §11 の承認ゲートへ（検分結果と差分の一覧を提示する）。承認後、整合チェッカーの `lock` で本実施単位の基準線（`spec.lock.json`）を採取する。

## 1. 設計の読み取りと変更検出
- 設計書は doctool 経由で最新化して読む（バイナリは `doctool cache`、md は原本直読）。
- 実施単位フォルダ直下の `sources.lock.json` を `doctool status --lock` で突き合わせ、差分があれば影響する導出単位・ケースを再導出対象として計画に組み込む。検出は自動・**是正は承認制**。lock がまだ無い場合（新規導出の初回）はこの照合をスキップし、§10 で新規作成する。
- **人手変更の関所**: `spec.lock.json`（承認基準線）と現物 xlsx を整合チェッカーで突合する——`PYTHONUTF8=1 python .claude/skills/testgen-plan/scripts/spec_integrity/spec_integrity.py check <実施単位dir>`。**要裁定差分**（承認後の追加・削除・改変。合否等の人の記入欄は対象外）が出たら、§9 より先に差分一覧を提示して**変更した理由を人に確認**し裁定する——採用（追加=容認して記帳／削除=対象外理由 or 再割当を伴う／改変=設計と突合し、仕様側誤りの是正なら不具合管理表へ起票）または差戻し（基準線の内容へ復元）。裁定はスキルが `ケース変更台帳.md` へ記帳し、同スクリプト `lock` で基準線を更新して閉じる（**人にメモ・台帳・lock の記入は求めない**）。裁定前に §9 の編集で人手変更を上書きしない。設計差分と人手差分が両方ある場合は人手差分の裁定を先に行う。lock が無い場合（新規導出の初回）はスキップ。
- 導出は**詳細設計を基準**、基本設計で補完。詳細設計の欠落は暫定判断せず**不備として報告**する。

## 2. 導出単位の棚卸し
- 詳細設計から機械的に列挙する（入力項目×検証ルール／画面イベント／サービス分岐・副作用・異常系／状態×操作）。
- **粒度**: 仕様書中の表は**1行＝1導出単位**として拾い、備考・但し書きは**文単位**で独立の導出単位にする（複数ボタン・複数部品の個別動作を1行に丸めない。書式の例外規定＝「◯◯の場合はそのまま」等の但し書きを本則の行に吸収しない）。
- **横断仕様の一元化**: システム共通仕様書群（画面部品・画面共通・API 共通・入力値チェック等）由来の導出単位は、**オーナー機能**（実施単位・配置規範の既定 `00_共通部品`）の棚卸しに一元化し、ケースは代表画面の操作として設計する。各画面機能の棚卸しには**画面固有の差分**（固有の列構成・入出力仕様の特記・部品既定の上書き）だけを立て、部品・共通仕様の一般挙動はオーナー機能の該当ケースへの横断参照（`` `00_共通部品` n-m `` の形。実在は整合チェッカーが検証）で閉じる。逆にオーナー機能から画面機能へ委譲する参照（「代表として◯◯でケース化する」等）は**行アンカー形式** `` `<機能>` #<棚卸し行>（<ケースID>） `` で書く（整合チェッカー C9 が、行の実在・行のケースID割当・ケースの実在を双方向に検証し、ケース再採番による参照の意味ずれを検出する）。同じ横断仕様を機能ごとに繰り返し棚卸しすると、抜けが全機能で相関する（各機能の突合で共通仕様が背景扱いになる）ため禁止する。
- 各単位を「出典／導出単位／観点分類／ケースID or 対象外理由」で扱う。観点分類は観点カタログのセクション区分を規定語彙とし、**入力チェック系の行（単項目・相関とも）は観点分類に「入力チェック」を含める**（整合チェッカー C10 の判定キー。棚卸し表に観点分類列が無いことはエラー）。**設計に無い単位を推測で作らない**。対象外候補は質問リストで確認する。

## 3. オラクルの確定（実装参照より先）
- 期待結果は**実装を参照する前に設計から確定**する。メッセージ・遷移先は文言正本から転記する。
- **仕様由来**（メッセージ・境界・遷移）は具体値で確定。**データ由来**（件数・並び・CSV本文）は母集団を実ファイル化し、算出した具体値を焼き込む（導出表現・プレースホルダ禁止）。
- 各期待結果に 可視／【機械検証】 の別を付す（上記規律2）。

## 4. ケース設計
- **同値分割→境界値**: 有効・無効同値クラスを列挙して代表値を選ぶ（境界は端と端±1 の対）。無効同値の定番（空／スペースのみ／前後空白／全半角／大小文字／改行・制御文字／サロゲートペア）を検討し、対象外は理由をメモへ。
- **正常・異常は対**で設計する: 入力チェックの各棚卸し行（項目×検証ルール。相関を含む）に、**そのルールに違反する異常系 ≥1 と、正当な入力が受理される正常系 ≥1** のケースを割り当てる（整合チェッカー C10 が機械検証。正常系は代表ケースの共有可＝同じケースIDを複数行に併記する。正常系のみではチェックが働くこと自体が、異常系のみでは正当入力の受理が未検証に残る）。異常系を設計できないように見える行も既定で対象外にせず、到達手段カタログと照合し、なお不能なものだけ質問リストで裁定を得る。入力チェックは原則1項目1ケースとし、期待結果に**否定の観測**（他項目のエラーが出ない・未登録・入力値保持）を含める。
- 相関チェックは組み合わせ（成立・不成立・境界・片方空）で設計し、**複数項目同時エラー**を最低1ケース確認する。状態×操作の直積は表で列挙してから間引き、根拠（同値・到達不能）をメモへ残す。
- **サーバー検証を軸**とし、バイパス手順は操作手順に明記。クライアント検証固有は観点欄に【クライアント検証】。
- 期待結果は画面から観測できる挙動に落とし、合否が一意に定まるよう書く（機械検証行を除く）。

## 5. セクション構成と採番
- 観点カタログを標準にセクション `n`／ケース `n-m` で採番する。

## 6. 実装との突合（到達可能性）
- ケース確定前に**アプリの実装**と突き合わせる。設計との食い違いは**差異一覧として情報提供**する——是正方向の確認・裁定は求めない（共有規範「設計と実装の乖離の扱い」）。期待結果は設計基準のまま確定し、E2E 実行時にテストの失敗として検出される見込みである旨を付記する（E2E テストの実装は突合対象ではない——この時点で存在しなくてよい）。
- 到達不能・観測不能に見える観点は、対象外と結論する前に**共有規範の「到達手段カタログ」と照合**する。カタログに到達手段（バイパス・別セッション・セッション失効・障害シーム・実行時生成・連続フレームによるスクロール到達）がある観点は対象外にせず、**手段を操作手順に明記して**ケース化する（シーム・部品が未実装であることは対象外理由にならない——exec が後工程で作る）。どの手段にも該当しないものだけを確認事項として質問リストへ挙げ、照合した手段と該当しない理由を添える。
- **対象外理由に「JUnit・結合テスト・目視等の E2E 以外で担保する」と書くことを禁止する**（共有規範「目的と範囲」——E2E が品質保証の主体——と矛盾するため）。E2E で扱わない判断はユーザーの裁定事項であり、スキルが既定値として選んではならない。

## 7. 入力データ・期待値の実ファイル確定
- 母集団を実ファイルで固定し、データ由来オラクルは具体値を焼き込む。参照は規約準拠の相対パスで明記し、`ケースID ↔ 入力データ ↔ 期待値` を記述だけで辿れるようにする。
- **データ事実表を経由して書く**: 本文に記入するデータ由来の値（ファイルサイズの表示文字列・件数・ID帯・行の具体値）は、記入の直前に整合チェッカーの facts（`PYTHONUTF8=1 python .claude/skills/testgen-plan/scripts/spec_integrity/spec_integrity.py facts <実施単位dir> [機能...]`）で実測一覧を生成し、**その出力からの転記のみ**とする。記憶・サブエージェントの要約・過去の下書きからの転記を禁止する（実物と異なる値の焼き込み＝事実ドリフトを防ぐ）。複数エージェントで作業を分担する場合も、値を書くエージェント自身に事実表（または正本）を読ませる。
- **順序**: データ正本（シード・素材・期待値）を確定してから本文を書く。本文記入後にデータ正本を変更した場合は §9 のデータ変更の関所を通す（事実表を再生成し、影響ケースを再確認するまで確定としない）。
- シード CSV の**全行に主キーを明示**する（自動採番依存の禁止）。
- データ正本のファイル名は、clone 先を問わずフルパスが Windows のパス長制限（260文字）に収まる長さとする。長名（ファイル名長の境界等）は実物を置かず、**内容の正本（短名）＋テスト実行時に指定名で生成**とし、生成名の構成を仕様書に明記する。

## 8. 網羅の証明
- **設計突合（機能単位・サブエージェント）**: 各機能の §2〜§7 を終える**たびに**行い、全機能の完了まで先送りしない（漏れの型は後続機能でも繰り返されるため、早期に検出して以降の導出へ反映する）。事実収集サブエージェントに「当機能の設計文書（詳細設計を基準、基本設計・システム共通仕様・画面部品仕様を含む）から振舞いを定める記述を番号付きで列挙し、棚卸し表と機械的に対応付け、対応する行が無い記述を【対応行なし】として原文引用＋出典付きで報告」させる。依頼は事実の収集と機械的な対応付けに限定し、「問題かどうか」の判断を依頼しない。各記述に転記／推測の別を付けさせ、原文引用と出典を伴わない指摘は採用しない。【対応行なし】は棚卸しへの追補（ケース化または対象外理由の記録）で解消し、判断に迷うものは質問リストへ。複数機能に共通する規則の見落としが見つかった場合は、導出済みの機能へも遡って適用する。**横断仕様（システム共通仕様書群）の突合はオーナー機能の棚卸しに対して一度だけ**行い、画面機能の突合では共通仕様由来の記述を「当機能の固有差分の行」または「オーナー機能の棚卸し行」への対応付けで閉じる（対応付け先としてオーナー機能の棚卸し表もサブエージェントに渡す）。
- **データ突合（機能単位・サブエージェント）**: 設計突合と同じ実行単位で、事実収集サブエージェントに「当機能の仕様書ケース本文からデータ由来の主張（ファイル名＋サイズ表示・件数・ID・日時・行の具体値）を番号付きで転記し、facts の実測一覧・データ正本と機械的に対応付け、【不一致】のみを原文引用＋実測値付きで報告」させる。依頼は転記と機械的な対応付けに限定し、「問題かどうか」の判断を依頼しない。【不一致】は本文またはデータの是正で解消する（散文に書かれた事実の網羅はこのパスが受け持ち、定型に整合チェッカー C7 が効く）。
- **突合の独立性と記録**: 設計突合・データ突合は、その機能の生成を担当していないコンテキスト（新規のサブエージェント）で実施する（生成した本人の再読は同じ思い込みを再生するため）。サブエージェントの報告全文は `<機能>/突合報告_設計.md`・`<機能>/突合報告_データ.md` として**証拠ファイルに保存**する（整合チェッカー C8 が実在を検証。「独立突合を実施した」という主張を後から再監査可能な証拠に変える）。結果は**突合記録**（対象文書・列挙件数・対応付け件数・【対応行なし】／【不一致】ゼロの確認、解消した場合はその旨）として各機能の導出判断メモに残し、§11 の提示物に含める。突合記録の統計は整合チェッカー `report` の機械実測と突合報告からの**転記のみ**とし、「解消済み」は該当変更が現物に反映されたことを `check` 再実行で確認してから記す（記載規律8）。
- 網羅と参照整合は整合チェッカーで**機械的に証明**する: `PYTHONUTF8=1 python .claude/skills/testgen-plan/scripts/spec_integrity/spec_integrity.py check <実施単位dir> [機能...]`。照合は双方向——①全導出単位がケースID または対象外理由を持つ（空欄ゼロ）②割当先ケースID（機能横断参照を含む）が仕様書に実在する ③仕様書の全ケースがメモ（または変更台帳の採用記録）から説明できる ④データ正本の孤児・参照切れが無い ⑤セクション内採番の欠番（警告）⑥本文のサイズ表記・シードの宣言サイズとデータ実測の一致（C7。実ファイル・シード宣言名にアンカーできた表記のみを保証し、アンカーできない散文は上記データ突合が受け持つ）⑦文中の棚卸し行番号参照（#n。質問リスト等の実施単位直下文書を含む）と証拠ファイル言及の実在（C8——「やったと書いたが現物に無い」記帳の検出）⑧行アンカー付き横断参照の双方向整合（C9——再採番による参照の意味ずれの検出）⑨観点分類が入力チェックの棚卸し行への正常系・異常系の対割当（C10——正常系のみ／異常系のみのカバー漏れの検出。判定は仕様書の正常/異常系列で、横断参照先も含める）。
- **指摘ゼロが §11 提示の前提**。生成時点の指摘は plan 自身の欠陥としてただちに是正する（人手変更に由来する要裁定差分は §1 の関所へ）。説明できない差は漏れの兆候として報告する。

## 9. 変更影響分析
- 変更のあった設計書を起点に影響ケースを特定し、再作成範囲を限定する。**既存ケースの一括削除・全再生成は禁止**（削除は理由付き候補として提示し承認後）。
- **データ正本の変更も関所を通す**: シード・ベースライン・素材・期待値ファイルを変更した場合、参照テストデータ列から当該ファイルを参照する全ケースを機械列挙し、facts を再生成して該当ケース本文のデータ由来の値（前提条件の件数・ID帯・サイズ表示等）を再確認する（§8 のデータ突合を該当機能へ再実行する）。本文が先・データ改訂が後になったときの取り残しをここで捕捉する。

## 10. 確定（記入・レイアウト・lock を同一ステップで）
- xlsx へ直接記入する（doctool `dump`/`fill`。人の記入を保存してセル単位更新）。
- レイアウト再構築（印刷範囲・行高の見切れ0検証・セクション見出しの結合・**列幅は雛形から変更しない**）。
- 実施単位フォルダ直下の `sources.lock.json` を `doctool hash` から組み立て、xlsx 記入と同一ステップで更新する（先送り禁止）。
- 整合チェッカーの `lock` で `spec.lock.json`（承認基準線: ケース行単位の内容指紋。No・観点・前提・手順・期待結果・参照データの plan 所有列のみ＝合否等の人の記入欄は対象外）を xlsx 記入と同一ステップで更新する。整合エラーが残る間は `lock` が拒否する。
