# 詳細設計書更新計画立案スキル

本スキルでは、**実装完了後に詳細設計書を実装へ追随させる作業（doc revision）のうち、更新計画の立案と乖離の検出**の方法論・手順を定める。
docgen 系（基本設計→詳細設計）・codegen 系（詳細設計→実装）と対をなし、docrev 系（docrev-plan / docrev-exec / docrev-check）は**実装を正本とした詳細設計書側の更新**を担う。

- 目的は実装と詳細設計書の差異を埋めることだが、**実装を詳細設計書に転写することではない**。
- 実装が正本である。実装は変更せず、詳細設計書のみを変更対象とする。
  - 実際の変更は docrev-exec が担う。**本スキルでは設計書・実装のいずれも変更しない**。
- テスト（テストコード・テスト成果物）は突合の対象外とする。

## スキルの前提

スキルの仕様には以下の前提を置く。前提を満たしていない場合はユーザーにその旨を告知し、指示を仰ぐ。

- 全ての詳細設計書が存在すること
  - 例: `docs/specs/詳細設計/`
- 詳細設計書の規約が存在すること
  - 例: 書式説明 `docs/specs/詳細設計_書式説明/`、凡例 `docs/specs/詳細設計_書式凡例/`
- 実装が完了していること

### スキル使用時のルール

- 本スキルは**調査と計画立案のみ**を行う。詳細設計書・実装・テスト・基本設計・凡例・書式説明の**編集は禁止**されている。
- 作業中にこのスキルやプロジェクト全体での指示で明確に定められていない事象に遭遇した場合は、自己判断せずユーザーに判断を仰ぐ。

## 乖離の判定規範

検出するのは、実装と詳細設計書が**明確に**乖離している点のみとする。詳細設計書の記述を解釈した範疇に収まる点は対象外。

- 実装の都合で分離・結合したコードは、それが詳細設計に著しく矛盾するものでなければ指摘不要。
  - 例1: 詳細設計の `ItemForm` クラスが実装では `ItemInputForm` や `ItemUpdateForm` などに分かれた場合、処理やデータ構造に矛盾がなければ指摘しない。
  - 例2: 詳細設計に定義された `ItemService` の `update` メソッドがなく、`ItemUpdateService#update` が存在する場合は指摘する。
  - 例3: 実装された `ItemService` の `register` メソッド内の処理フローが詳細設計書の定義と異なる場合は指摘する。
- 判定の目安: **設計書だけを読んで実装した実装者が、現行実装と論理的に等価な成果に到達できるか**。
  - 到達できる → 乖離ではない（命名・分割粒度の揺れ、実装手段の差）。
  - 到達できない → 乖離（処理フロー・条件・分岐・データ構造・入出力の不一致、設計書に無い実装機能、実装に無い設計記述）。
- 詳細設計は実装手段に依存しない論理構造で書かれる（docgen-exec「記載粒度の原則」）。言語・フレームワーク固有の表現差は乖離として扱わない。

## 中間生成物の配置場所の作成

本スキルおよび docrev 系スキル（docrev-exec / docrev-check）が共有する中間生成物は、
**リポジトリルート直下の `.doc-revision/` 配下**に配置する。対象が存在しない場合はこれを作成する。
また `.doc-revision/` には `.gitignore` を配置し、配下のファイルはリポジトリ管理対象とされないようにする。

- `.doc-revision/plan/` … 機能別の更新計画と乖離の検出結果（本スキルが生成）
- `.doc-revision/progress.md` … 進捗・決定台帳（本スキルが初期化し、docrev-exec が工程ごとに更新する）

## 設計書の読み取り

- **設計書は読む時に doctool を経由して最新化する**（事前一括変換はしない）。バイナリ（docx/xlsx）は `doctool cache <src>`（未変更ならスキップ＝安価）を通してから、出力された `.doctool-cache/<相対パス>.md` を読む。**`.doctool-cache/` の .md を doctool を通さず直接読まない**（最新性を担保するため）。md／テキストは複製せず**原本を直接読む**。
- 突合の一次参照は上記のキャッシュとし、判断を左右する箇所は正本（docx）を doctool で再読して確定する。サブエージェントに事実収集を依頼する場合も、同じ手順（cache 経由で読む）を指示する。

## 作業手順

引数で機能名が指定された場合は、§2 の更新計画が作成済みであることを確認した上で、当該機能の §3（乖離の検出）から実施する。

### 1. 既存の成果物の確認

`.doc-revision/` 配下に既存の成果物がある場合、作業の続き（未検出機能の乖離検出 等）なのか、最初からやり直すのかをユーザーに確認する。
やり直す場合も、`.doc-revision/progress.md`（進捗・決定台帳）の**既存の「決定ログ」「申し送り」を引き継ぐかをユーザーに確認**する（過去の横断的決定が失われると後続工程の手戻りを招くため）。

### 2. 全体俯瞰と更新計画の作成

プロジェクトの構成を把握し、更新計画を作成する。**具体的な突合は次工程（§3）に任せ、まずは全体を俯瞰して計画する。**

- コードベースに実装計画（例: `.codegen/plan/`）がある場合はそれを参考にしてよい（機能一覧、機能と定義書・実装の対応関係の手がかりになる）。
- 計画の粒度は機能別とし、機能ごとに `.doc-revision/plan/機能別計画_<機能名>.md` に保存する。以下を明確に記述する。
  - 機能の概要
  - 関連する詳細設計書の一覧（定義書単位。ファイルパスを明記）
  - 関連する実装の一覧（クラス／ファイル単位。ファイルパスを明記）
  - 複数機能で共有される要素（型・テーブル・DBIF・共通サービス 等）の扱い: どの機能の計画で突合するかを一意に定め、重複突合・突合漏れを防ぐ
  - 突合の観点（処理フロー・データ構造・入出力・分岐/異常 等、当該機能で特に確認すべき点）

### 3. 乖離の検出

更新計画を基に、機能ごとに詳細設計書と実装を突合し、乖離の判定規範に該当する点を検出して当該機能の `.doc-revision/plan/機能別計画_<機能名>.md` に追記する。

- 突合の事実収集にはサブエージェントを活用してよい。その際は**収集と判断を分離**する: サブエージェントには「設計書の記述と対応する実装箇所の転記（原文引用＋出典: ファイル名・位置）」を依頼し、**乖離か否かの判断は本スキルを実行するエージェントが判定規範に基づき行う**。「問題点を挙げよ」という依頼は過剰検出を招くため行わない。
- ユーザーに報告する乖離点は、報告前に正本（設計書・実装）の該当箇所を再読して確定する。
- 検出した結果には以下の項目を含める。
  - 乖離点と、対応する詳細設計（ファイルパス＋該当箇所）・実装（ファイルパス＋行）へのリンク
  - どのように乖離しているかの説明（設計書の記述と実装の挙動を対比して記す）
  - 修正案（詳細設計書側をどう変更するか）
  - 変更による影響範囲の説明（当該設計書内の他記述、一覧表（索引）、他の定義書への波及）

### 4. ユーザーへの報告と修正対象の判断

検出結果の出力後ユーザーに報告し、**どの点を修正するのか判断を仰ぐ**。

- 乖離点ごとに「修正する／見送る」の判断を得て、判断結果を機能別計画に記録する。
- 判断を得ていない乖離点を修正対象として扱わない。

### 5. 進捗台帳の初期化・更新

ユーザーが修正すると判断した項目を工程として `.doc-revision/progress.md` に登録する。台帳が無ければ初期化し、あれば追記する。
docrev-exec が着手時に参照し（次の未着手工程の特定・決定の踏襲）、工程完了ごとに更新する。

- **工程進捗**: 修正対象の各項目を機能単位でまとめ、`- [ ] 工程N <機能名: 乖離点の概要>` の未着手チェックボックスとして列挙する。
- **決定ログ**: 横断的に効く確定事項（乖離判定の解釈・用語の扱い・共有要素の帰属 等）を記録するセクションを用意する（docrev-exec が工程ごとに追記）。
- **成果物の所在 / 技術メモ / 申し送り**: それぞれ空セクションを用意する。

> この台帳は中間生成物であり `.doc-revision/` 配下（リポジトリ管理対象外）に置く。

### 6. 出力の検証

出力した成果物に対して再度全体を俯瞰し、以下を確認する。

- 機能間で判定がぶれていないか（同種の差分を一方の機能では乖離とし、他方では見送っていないか）
- 突合漏れがないか（どの機能の計画にも属さない詳細設計書・実装が残っていないか）

結果についてユーザーにレポートし、内容の承認を得る。
docrev-exec による更新に入る前に、チャットのコンテキストを切り落とすようユーザーに推奨する。
