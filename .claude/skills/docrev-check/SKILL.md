# このドキュメントについて

> **実装を正本とした詳細設計書更新（docrev-plan / docrev-exec）の全作業完了後に、全体を通じたレビューを実施する際の規約と作業手順**を定める。

## このスキルについて

docrev-exec による全ての更新作業の完了後に、更新結果を客観的にレビューする。
本スキルでは**設計書の修正は行わない**。検出した事項は想定される対処方法とセットでユーザーに通知し、対応の是非・方法はユーザーに委ねる。

以下にこのスキルの動作プロセスを記載する。

### 1. レビュー対象と正本の準備

- 進捗・決定台帳 `.doc-revision/progress.md` と `.doc-revision/plan/` 配下の機能別計画を読み、更新された設計書の一覧と、ユーザーが修正すべきと判断した乖離項目を把握する。
- 更新後の詳細設計書のテキスト化:
  - **設計書は読む時に doctool を経由して最新化する**（事前一括変換はしない）。バイナリ（docx/xlsx）は `doctool cache <src>`（未変更ならスキップ＝安価）を通してから、出力された `.doctool-cache/<相対パス>.md` を読む。**`.doctool-cache/` の .md を doctool を通さず直接読まない**（最新性を担保するため）。md／テキストは複製せず**原本を直接読む**。
  - 判断を左右する箇所は正本（docx）を doctool で再読して確定する。
  - このとき `_old` や `bak` などのディレクトリ配下または zip ファイルにある旧バージョンは対象外とする。
- 実装はリポジトリのソースコードを正本として参照する（テストは対象外）。

## 2. レビューの進め方

以下の観点で、更新箇所に限定せず全体を通じて確認する。

1. **更新結果の突合**: 修正対象と判断された乖離項目がすべて解消されているか。`.doc-revision/progress.md` の工程・機能別計画の修正案と、更新後の設計書を照合する。
2. **設計書全体での整合性の確認**:
   - 索引（一覧表）と個別定義書が 1:1 で対応しているか（追加・改名・削除が索引へ反映されているか）
   - 同一対象を指す名称・型・テーブル・相互参照が設計書間で食い違っていないか
   - 更新した定義書と、更新対象外だった関連定義書との間に新たな矛盾が生じていないか
3. **設計書の自立性**: 設計書が実装に依存せず、設計書単独で成り立っていること。
   - 実際のプログラム・SQL 文・言語固有のメソッド名・型名などの実装依存記述が本文に混入していないか
   - 実装コードやそのファイルパスを参照しないと理解できない記述がないか
   - 設計書だけを読んで解釈のブレなく実装できる粒度か（docgen-exec「記載粒度の原則」）

## 3. 検出事項の扱い

内容に矛盾・不足があった場合は、それを書き留めて、想定される対処方法とセットでユーザーに通知する。

- 各指摘には**根拠（設計書の出典: ファイル名＋位置、実装が関わる場合は該当箇所: ファイルパス＋行）**を必ず添える。
- 「事実（設計書間・設計書と実装の差分）」と「解釈（こうすべきという推測）」を区別して報告する。
- 実際の対応（設計書の修正）は行わず、対応の方法や実施の是非はユーザーに委ねる。修正が承認された事項は `.doc-revision/` の機能別計画・進捗台帳に追記した上で、docrev-exec で対応する。
