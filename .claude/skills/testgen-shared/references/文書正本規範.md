# 文書正本規範

テスト内容の導出・検分がプロジェクトの文書に依存するとき、その文書を**パスではなく役割
(ロール)で指定し、プロジェクトから探索して解決する**ための規範。スキル文書・キットに
プロジェクトの実パスを書くことは禁止する(依存の向きは常に プロジェクト → スキル)。

## 文書ロール

| ロール | 内容 | 識別の手がかり | 必須性 |
| --- | --- | --- | --- |
| 詳細設計 | 分岐・計算規則・対応関係(コントローラー定義書・処理定義等) | 名称・見出しに「詳細設計」、画面/処理単位で分岐や規則を定める内容 | 必須(導出の基準) |
| 基本設計/画面レイアウト | 画面項目一覧(項目名・ラベル・部品種類・入出力仕様)の表 | 名称に「画面レイアウト」、画面項目の表を持つ | 必須 |
| 基本設計/機能仕様 | 機能の振舞い・入力値チェック・処理の仕様 | 名称に「機能仕様」 | 必須 |
| 基本設計/システム共通仕様 | 画面部品・入力値チェック・API 応答等の横断仕様 | 名称に「共通仕様」 | あれば用いる |
| 基本設計/画面モックアップ | 視覚の実体(html 等のモック、スクリーンショット) | モック実体ファイル群、名称に「モックアップ」 | あれば用いる |
| 基本設計/エンティティ定義 | エンティティ・項目定義 | 名称に「エンティティ」「ER」 | あれば用いる |
| テストケース様式 | テスト仕様書の書式説明・書式凡例・仕様書雛形 | 名称・見出しに「書式」「凡例」「様式」「雛形」、テスト仕様書の記法を定める内容 | **plan に必須。既定なし** |
| テスト規約 | プロジェクトによる本規範群の上書き・具体化 | 名称・見出しに「テスト」+「規約」 | 任意(無ければ既定で動く) |

- ロール名は役割の概念であり、プロジェクトの文書名・フォルダ構成は自由。手がかりへの
  完全一致を要求しない。
- **テストケース様式が見つからない場合、様式を即興で発明してはならない**。停止して
  ユーザーに所在を確認する。

## 解決手順

1. **探索**: 手がかり(名称・見出し・内容特徴)でプロジェクト内の候補を収集する。
2. **判別**: 候補の内容を確認してロールに合致するものを特定する。一意なら採用。
3. **停止**: 候補が複数で判別できない、または必須ロールがゼロ件のときは、自己判断せず
   ユーザーに確認する(「テスト規約」ロールのみ、ゼロ件は正常であり既定で動く)。
4. **固定**: 解決結果(ロール・パス・内容指紋)を実施単位の `sources.lock.json` に記録する。
   以後の作業は lock の解決結果を優先し、指紋の不一致は「設計変更の検出」として扱う
   (毎回の再探索はしない。探索の非決定性を初回に閉じ込めるため)。

## 正本の優先順位

テスト内容(分岐・判定・期待結果)の導出は**詳細設計を基準**とする。基本設計は
**画面遷移・画面レイアウト・視覚(モックアップ)**の正本として、詳細設計で判別できない
事項の補完に用いる。

- **詳細設計**(分岐・計算規則・対応関係)… テスト内容導出の基準
- **基本設計**(画面遷移・画面レイアウト・イベント定義。視覚はモックアップ)… 画面構造・
  遷移・視覚の正本/詳細設計の補完
  - 基本設計内の役割分担: **文言(ラベル・メッセージ・見出し等の文字列)は画面レイアウト
    本文(画面項目一覧等の表)が正本**。モックアップの正本性は**配置・寸法・スタイル等、
    表や文章で表現されない視覚表現に限る**。両者が食い違う場合は基本設計内の不整合であり、
    モックアップ優先とはせず、下記の正本どうしの食い違いとしてユーザーに確認する。
- **テストケース仕様**(本スイートの成果物)
  - 本文 ＝ docx/xlsx(人間正本・印刷可)
  - データ ＝ csv(正本)。アプリ取込/出力用はアプリ様式に厳密準拠のバイト列、seeder 用
    ベースラインは DB 表スキーマ準拠。**ケースID 列は課さない**。ケースID↔データ↔期待値の
    対応は仕様書の参照テストデータ列で辿る。

基本設計と詳細設計が食い違う場合は、詳細設計を基準にテストを導出しつつ差異を報告する。
**その他の正本どうしの食い違いは自己判断せずユーザーに確認する。**

## 設計入力の扱い

- 観点導出の入力は、基本設計(画面遷移・画面レイアウト・イベント定義)、詳細設計(論理)、
  視覚はモックアップ。
- **テスト内容の導出は詳細設計を基準とする**。詳細設計の欠落・記載不足は暫定判断せず
  **その不備を報告**する。
- **設計上、動作テストすべき項目は必ずテスト項目として記載**し、省略しそうな項目は逐次
  ユーザーに確認する。
- 期待結果は画面から観測可能な実挙動(実装の正確な文字列)で確定する。操作手順も**画面で
  観測可能な操作**として書く(「datalist を確認する」等の内部検査表現は禁止)。
