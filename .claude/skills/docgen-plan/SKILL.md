# 詳細設計作成計画立案スキル

本スキルでは **詳細設計を作成する前の計画立案** の方法論・手順を定める。

## スキルの前提

スキルの仕様には以下の前提を置く。前提を満たしていない場合はユーザーにその旨を告知し、指示を仰ぐ

- 完成済みの基本設計書があり、コードベース中の特定のディレクトリ内に存在すること
- 詳細設計の雛型(フォーマット・凡例・ルールなど)が定められていること

### スキル使用時のルール

- 基本設計書および詳細設計の雛型の**編集は禁止**されている。
  - それらの中で誤りがある場合はユーザーに対応を促す
- 作業中にこのスキルやプロジェクト全体での指示で明確に定められていない事象に遭遇した場合は、自己判断せずユーザーに判断を仰ぐ

## 詳細設計について

### 目的

詳細設計の作成にあたり、システム全体を俯瞰した上で
該当機能の作成に必要な要素を事前に洗い出し、実施にあたってその作業概要を明らかにする

## 中間生成物の配置場所の作成

本スキルおよび docgen 系スキル(docgen-check / docgen-exec)が共有する中間生成物は、
**リポジトリルート直下の `.docgen/` 配下**に配置する、対象が存在しない場合はこれを作成する。
また`.docgen/` には `.gitignore`を配置し、配下のファイルはリポジトリ管理対象とされないようにする。

- `.docgen/plan/` … 作成計画(本スキルが生成)
- `.docgen/progress.md` … 進捗・決定台帳(本スキルが初期化し、docgen-exec が工程ごとに更新する)
- `.docgen/sources.lock.json` … 各詳細設計が依拠した基本設計の {相対パス, role(primary), sha256} の記録。**`doctool hash` が機械生成し手編集しない**(docgen-exec が工程完了時に記録)。設計変更を検出するベースライン。

## 作業手順

### 1. 既存の成果物の確認

既存の成果物がある場合、gitignoreの設定を除き削除した上で以降の内容を再度実施して最新化する。
ただし `.docgen/progress.md`（進捗・決定台帳）を再生成する場合は、**既存の「決定ログ」「申し送り」を引き継ぐかをユーザーに確認**する（過去の横断的決定が失われると後続工程の表記ゆれ・手戻りを招くため）。

### 2. 基本設計書(仕様)の読み取りと変更検出

リポジトリ内を探索して基本設計書を配置しているディレクトリを明らかにする。見当たらない場合はユーザーに尋ねる。`_old`や`bak`などのディレクトリ配下またはzipファイルにある旧バージョンは対象外とする。

- **設計書は読む時に doctool を経由して最新化する**（事前一括変換はしない）。バイナリ（docx/xlsx）は `doctool cache <src>`（未変更ならスキップ＝安価）を通してから、出力された `.doctool-cache/<相対パス>.md` を読む。**`.doctool-cache/` の .md を doctool を通さず直接読まない**（最新性を担保するため）。md／テキストは複製せず**原本を直接読む**（ドキュメントから参照される画像等のバイナリは読む時に必要なら複製する）。
- **着手時の変更検出（reconciliation）**：`.docgen/sources.lock.json` に対象の記録があれば、記録された基本設計の指紋を、同 lock に対する `doctool status --lock`（changed/missing があれば変更あり・終了コード1）で突き合わせる。差分があれば、その基本設計から作った詳細設計の再点検を要すると洗い出し、**計画に組み込む**。検出は自動・是正は承認制。基本設計の誤りは編集せずユーザーに対応を促す。

### 3. 全体レベルの詳細設計の作成計画立案

システム全体の仕様を調査し、システムの体系を理解した上で詳細設計の作成計画を立案する。
以下の内容を調査してまとめ`.docgen/plan/全体計画.md`に出力する

- プロジェクトの名称や達成したい目的
- 機能間の共通仕様(セキュリティや認可などシステム共通の機能)
- システムが持つ機能の一覧およびそれらのグループ関係
- 機能グループごとの成果物配置規約: イベント定義書配下の定義書（コントローラー/サービス/画面イベント定義書）を機能グループ別サブフォルダに分類するための「機能グループ→連番接頭辞」対応表。連番は基本設計の画面フォルダ採番等の既存規約と整合させる。型・テーブル・DBIF など複数機能で共有する要素は対象外とする。あわせて、画面イベント定義書のように1機能グループ内で細分単位（画面等）ごとに多数生じる種別については、機能グループの下に細分（画面）サブフォルダを設けるための「画面→連番」対応表も定める。

### 4.個別機能レベルの作成計画立案

全体レベルの調査によって明らかとなったシステムがもつ機能の一覧に対して
以下の内容を調査してまとめ`.docgen/plan/機能別計画_<機能名>.md`に出力する

- 機能ごとに詳細設計作成時に必要となる以下の内容を明らかにする
  - 依存する機能の有無および対象機能の一覧
  - インプットとする基本設計書
  - アウトプットとする詳細設計書（出力先パスを含む。機能グループに帰属する定義書は全体計画の配置規約に従い `<種別>/<連番_機能グループ>/` 配下、画面イベント定義書はさらに `/<連番_画面>/` 配下とする）
  - 既存の詳細設計書
    - 加筆にとどまらず既存の記述を修正する場合は、修正によって発生する影響を明確にする。
    - 基本設計の変更と矛盾が発生しない限り、既存の設計を大きく変えることは避ける。

### 5. 全体戦略と設計書の更新

個別機能の調査によって明らかになった情報を元にそれぞれの機能の依存関係から
推奨される作業の順序、機能の作成順序を紐解く。
全体レベルの設計書に以下の内容を追記する

- 個別の機能の推奨される着手の順序

加えて詳細設計書を作成するディレクトリの直下に`UML`ディレクトリがない場合はこれを作成し、
以下の内容を作成または更新して格納する。

- 主要なクラス図
  - クラス数が多くなると視認性が悪くなるため、複数の図に分ける
- シーケンス図
  - 機能ごとにファイルを分ける
- 画面遷移図
- ER図

### 5.5 進捗台帳の初期化

詳細設計生成の進捗と横断的決定を一元管理する台帳 `.docgen/progress.md` を生成する。
docgen-exec が着手時に参照し（次の未着手工程の特定・決定の踏襲）、工程完了ごとに更新する。

- **工程進捗**: §5 で定めた推奨着手順の各工程を、`- [ ] 工程N <概要>` の未着手チェックボックスとして Phase 単位で列挙する。
- **決定ログ**: 横断的に効く確定事項（命名規約・機能グループの扱い・機能グループ別フォルダ配置と連番対応表・型方針・索引運用 等）を記録するセクションを用意する（docgen-exec が工程ごとに追記）。
- **成果物の所在 / 技術メモ / 申し送り**: それぞれ空セクションを用意する。

> この台帳は中間生成物であり `.docgen/` 配下（リポジトリ管理対象外）に置く。

### 6. 出力の検証

出力した成果物に対して再度全体を俯瞰してシステムの設計に矛盾や問題がないか確認する。
結果についてユーザーにレポートし、内容の承認を得る。
このプランの実行後、詳細設計書の生成に入る前にチャットのコンテキストを切り落とすようユーザーに推奨する。
