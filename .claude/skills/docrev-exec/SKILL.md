# このドキュメントについて

> **docrev-plan が検出しユーザーが修正すべきと判断した乖離項目に基づき、詳細設計書を作成・更新する際の規約と作業手順**を定める。
> 引数に機能の指示がない場合は進捗・決定台帳 `.doc-revision/progress.md` の工程進捗から未着手の1工程を実施する。
> 1工程ずつユーザーに承認を受けて実行する。

## このスキルについて

- docrev-plan により策定された更新計画と乖離の検出結果（`.doc-revision/plan/` 配下）に基づき動作する。
  - docrev-plan が実行されていない、または修正対象がユーザーによって判断されていない場合は、docrev-plan の実行を先行させる。
- **更新するのはユーザーが修正すべきと判断した項目のみ**。作業中に新たな乖離に気付いた場合は勝手に直さず、docrev-plan の検出結果と同じ様式でユーザーに報告し、修正の是非の判断を仰ぐ。
- 実装が正本である。**実装・テスト・基本設計・凡例・書式説明は変更しない**。
- **進捗・決定台帳 `.doc-revision/progress.md` を着手前に読み（次の未着手工程の特定・「決定ログ」の踏襲）、工程完了後に更新する**（後述 §3）。台帳が無い場合は docrev-plan の実行を促す。
- 作業の進捗を台帳に記録し、**セッションをまたいでも作業が継続できるようにする**。

## 正本の優先順位

詳細設計書の更新の判断は以下の優先順位で正本に従う。

1. **実装（コード）** … 記述内容（論理）の正本。ただし転写はしない（後述「記載粒度の原則」）。
2. **詳細設計の規約（書式説明・凡例）** … 書式・様式・記載ルールの正本。
3. **基本設計** … 上流仕様。実装が基本設計とも矛盾している疑いがある場合は、設計書の更新に進まず立ち止まりユーザーに報告する（実装側の誤りの可能性があるため）。

## 記載粒度の原則（転写の禁止）

実装から設計書へ反映する際は、実装依存の記述が最も混入しやすい。docgen-exec「記載粒度の原則」に従い、実装の論理構造を**実装手段に依存しない記述へ翻訳して**書く。

- 実際のプログラム・SQL 文・言語固有のメソッド名・型名を設計書本文に書かない。制御条件・分岐・繰り返し・対応関係・計算規則を、概要で済ませず曖昧さなく定義する。
- 物理名（型・クラス・メソッド・テーブル/列・エンドポイント 等）は、その様式が物理名を記載する欄を持つ場合のみ、命名規則に適合する識別子として記載する。物理名欄に自然言語を書かない。
- セルフチェック: 複数の実装者が読んで**同じ実装に収束するか**。分岐の余地が残るなら粒度不足。

## 更新の実務（doctool）

詳細設計書（docx）の読み取り・解析・更新にはツール **doctool** を用いる。

- **内容の把握**: 対象定義書を読む際は `doctool cache <src>`（未変更ならスキップ＝安価）を通して `.doctool-cache/<相対パス>.md` を読む。編集座標の特定には `dump` の IR を用いる。
- **既存定義書の更新**: 対象ファイルを `dump` して IR を読み、修正対象の座標（part / block / row / col）を特定して記入スペック（`setCell` / `setParagraph` / `deleteBlock` / `fillTable`）を作成し、`fill` で出力する。既存文書のレイアウト・罫線・書式を完全継承し、ゼロから作り直さない。
- **定義書の新規作成**（実装に存在する要素が設計書に無い乖離を解消する場合）: docgen-exec の生成手順に従い、対応する凡例を `analyze` した上で雛形として `fill` で作成し、docgen の配置規約（機能グループ別フォルダ・連番対応表）に従って配置する。
- **一覧表（索引）との整合**: 個別定義書を作成・更新・改名・削除した場合は、対応する一覧表の該当行を追加・更新・削除する。
- 更新後に自動採番の地続き（表をまたいだ連番継続）が生じた場合は `doctool normalize` で是正する。
- 解析で判定できない特殊構造（テキストボックス・特殊フィールド・入れ子表 等）は、推測で埋めずユーザーに確認する。

## 3. 作業の進め方

> **更新の承認ゲート（最優先・厳守）**: 詳細設計書の作成・変更（`doctool fill` の実行）は、**直前のユーザー発言に明示の更新許可**（例:「更新OK」「進めて」）がある時のみ実行する。**部分的な修正指示・質問への回答・沈黙を「残りの暗黙承認」と解釈して更新に進んではならない**。修正指示を受けたら、その反映後に改めて明示の許可を求める。判断に迷う場合は更新せず確認する。

1. **着手時に `.doc-revision/progress.md` を読む**: 引数で機能が指定されない場合は工程進捗から**次の未着手工程**を選ぶ。あわせて「決定ログ」を読み、判断・方針を踏襲する（機能間の判断のぶれ・再導出を防ぐ）。
2. 更新前に計画を立て、対象の乖離項目・修正案・影響範囲を説明して合意を得る。
3. 機能別計画の修正案に従い、実装を正本として詳細設計書を作成・更新する。修正案が実装の現状と食い違う場合は立ち止まり、ユーザーに報告して指示を仰ぐ。
4. 更新後、更新箇所とその周辺の**目視確認**を行う（書式・表構成が崩れていないこと、意図した箇所のみ変わっていること）。
5. 続けて後述の**セルフチェック**を行い、全観点を満たすことを確認してから完了とする。
6. **完了時に `.doc-revision/progress.md` を更新する**: 当該工程を `- [x]` に変え、成果物パスを記録し、本工程で生じた横断的決定・技術メモ・申し送りを各セクションへ追記する。台帳更新は更新後の事実記録であり承認ゲートの対象外（設計書の更新自体は明示許可時のみ）。
7. 判断に迷う点・規約に無い事項は、勝手に決めずユーザーに確認する。
8. 個人情報・認証情報・シークレットは設計書・ログに残さない。

### 3.1 セルフチェック

作成・更新した設計書について、機能ごとに以下の観点を検証する。
満たさない点があれば、勝手に取り繕わず直す（直し方が不明なら勝手に決めずユーザーに確認する）。

- **規約に沿っていること**: 書式説明（例: `docs/specs/詳細設計_書式説明/`）の各様式ルールに適合し、レイアウト・表構成・記法が凡例と同一であること。
- **実装と矛盾していないこと**: 当該工程の乖離が解消されており、かつ修正によって設計書と実装の間に**新たな矛盾**が生じていないこと。
- **実装依存記述の非混入**: SQL・言語固有のメソッド名・型名などが本文に混入していないこと（「記載粒度の原則」）。
- **索引との整合**: 個別定義書と一覧表（索引）が 1:1 で対応していること。
- **名称の自己整合**: ファイル名・ヘッダー・本文で同一対象を指す表記が食い違っていないこと。
