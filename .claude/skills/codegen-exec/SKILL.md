# このドキュメントについて

> **詳細設計を正本としてコード（実装＋テスト）を作成・更新する際の規約と作業手順**を定める。
> 引数に作成する機能・定義書の指示がない場合は codegen-plan の全体計画における推奨着手順をなぞり、未着手の**1工程（定義書単位）**を実施する。
> **1工程ずつユーザーに承認を受けて実行する。**
> 本スキルでは**設計書（基本設計・詳細設計・実装規約）の作成・修正は行わない**。

## 記号の表記規約
本書では2種類のプレースホルダを使い分ける。
- `{{X}}` … **プロジェクトで一度決める固有値**。リポジトリ上のドキュメントに記載がなく判断出来ない場合は確認する。
- `<X>` … **成果物ごとに毎回埋める変数**。実装する対象に応じて埋める（例: `<クラス名>`）。

## このスキルについて

- codegen-plan により策定された実装計画に基づき動作する。
  - codegen-plan が実行されていない、最新化されていない場合は独立した別のエージェントでこれの実行を先行させる。
- 詳細設計書を正本として、当該定義書に対応するコードとテストを実装する。
- 型・共通部品・テーブルアクセス等は複数機能で共有される。**既に実装済みなら再利用し、重複実装しない**（変更があれば編集する）。
- **進捗・決定台帳 `.codegen/progress.md` を着手前に読み（次の未着手工程の特定・「決定ログ」の踏襲）、工程完了後に更新する**（後述 §4）。台帳が無い場合は codegen-plan の実行を促す。

## 正本の優先順位
実装の判断は以下の優先順位で正本に従う。下位が上位と矛盾する場合は実装に進まずユーザーに差し戻す。

1. **基本設計** … システムとして実現すべき仕様
2. **詳細設計** … 機能の論理構造（抽出条件・分岐・対応関係・計算規則 等）。実装の主たる正本。
3. **実装規約（コーディング規約・実装共通規範）** … 実装手段（言語・フレームワーク）に踏み込む規範。共通部品の所在・命名・レイヤ責務 等。

## 実装粒度の原則
詳細設計は実装手段に依存しない論理構造で書かれている。本スキルはそれを**規約に従って実装手段へ忠実に落とす**。

- **詳細設計の論理を取りこぼさない**：抽出/検索条件・並び替え・ページング・入出力変換・分岐/異常の各規則を、設計書の記述どおりに実装する。設計に無い挙動を勝手に足さない。
- **設計に書かれていない実装判断は規約に従う**：詳細設計が言語非依存ゆえ表現していない事項（共通部品化・型の物理表現・例外処理の様式 等）は、実装規約の正本に従う。規約にも無ければユーザーに確認する。
- **既存実装のパターンに倣う**：同種の既存実装がある場合はそのレイヤ構成・命名・記法に倣う。逸脱が必要なら着手前に明記して合意を取る。
- **DRY**：2箇所以上で同型の実装が現れる場合は共通部品へ切り出してから委譲に置き換える（規約「再利用・重複排除」に従う）。1箇所限定・将来再利用が見込めないものは無理に共通化しない。
- **提供UI成果物の流用（視覚の正本）**：基本設計・詳細設計に画面モックアップ／画面レイアウト定義／HTML・CSSサンプル等の具体的なUI成果物がある場合、それを画面の**視覚仕様の正本**として扱う。提供物の配色・フォント・レイアウト・寸法・構造・クラス語彙を流用・移植して見た目を一致させ、UIをゼロから起こし直さない、また確認は生成するページと対象となる見た目の比較は実際にレンダリングして確認する。スタイル値（色・余白・サイズ）は手で再発明せず提供物から転記する。採用フレームワーク上での再現は可（提供HTMLを丸ごと使う必要はない）で、フレームワーク差（Thymeleaf化・アセット配信・サーバ連携）に伴う最小限の改変のみ許容する。モックアップで静的な動的挙動（並び替え・ページング等）は、見た目を保って実装側で補う。採用したデザイン基盤の所在・方針（デザインシステムの場所、配色トークン、再利用するクラス）は `progress.md` 決定ログに記録し、以降の画面工程で再利用する。**論理は詳細設計／視覚はモックアップ**をそれぞれ正本とし、両者が食い違う場合は自己判断せずユーザーに確認する。

## 1. 入力と成果物

codegen-plan において作成した計画（プロジェクトルートの `.codegen/plan/` 配下）を参考にする。
およそ以下のような内容に収まるはずである。

- 入力
  - 詳細設計書（型情報定義書・テーブル定義書・データアクセス定義書・イベント定義書・画面定義 等）＝実装の正本
  - 基本設計書（詳細設計の元となった上流仕様）
  - 実装規約（リポジトリ内の正本。所在が不明な場合はユーザーに確認する）
  - 進捗・決定台帳 `.codegen/progress.md`（codegen-plan が初期化。次の未着手工程・横断的決定の参照元）
- 成果物: 実装コードとテストコード。既存実装のパッケージ構成・命名規約・記法に倣って配置する。

## 2. 実装の進め方（工程単位）

工程の単位は **詳細設計の定義書単位**とする。1工程で、対象定義書に対応する実装とテストを作成・更新する。

- **着手時の変更検出（reconciliation）**：`.codegen/sources.lock.json` に対象の記録があれば、記録済み指紋を、同 lock に対する `doctool status --lock`（changed/missing があれば変更あり・終了コード1）で突き合わせ、前回実装時から詳細設計・基本設計が変わっていれば影響を洗い出して本工程に取り込む（変更が大きく計画に関わる場合は codegen-plan の再実行を促す）。**設計書は doctool を経由して最新化して読む**（バイナリは `doctool cache` 経由・`.doctool-cache/` の .md を直接読まない、md／テキストは原本直読み）。
- 対象定義書の詳細設計を読み、論理構造を把握する。
- 依存する共有要素（型・共通部品・テーブルアクセス）が未実装なら、計画の着手順に従い先行工程として実施済みであることを確認する。未実装の依存が判明した場合は立ち止まり、着手順をユーザーと調整する。
- 既存実装を確認し、再利用できるものは再利用、更新が必要なものは影響範囲を確認の上で編集する。
- 実装に対応するテストを作成する（後述 §3）。

## 3. テストの方針
- 各実装に対し、詳細設計の論理（条件・分岐・計算規則）を検証するテストを作成する。
- 観点は **正常系・境界値・異常系**を網羅する。詳細設計が定める分岐・例外の判定基準をテストケースに落とす。
- 既存のテストの書き方・命名・配置に倣う。テストフレームワーク・実行コマンドはプロジェクト設定に従う。
- テストは実装の意図を表す正本として扱い、設計に無い挙動を固定化しない。

## 4. 作業の進め方

> **実装の承認ゲート（最優先・厳守）**: コード／テストの作成・変更（ファイルの生成・編集）は、**直前のユーザー発言に明示の実装許可**（例:「実装OK」「進めて」）がある時のみ実行する。**部分的な修正指示・質問への回答・沈黙を「残りの暗黙承認」と解釈して実装に進んではならない**。修正指示を受けたら、その反映後に改めて明示の許可を求める。判断に迷う場合は実装せず確認する。

1. **着手時に `.codegen/progress.md` を読む**：引数で機能・定義書が指定されない場合は工程進捗から**次の未着手工程**を選ぶ。あわせて「決定ログ」を読み、命名・方針・共通部品の扱いを踏襲する（再導出・ドリフトを防ぐ）。
2. 実装前に計画を立て、方針・影響範囲・リスクを説明して合意を得る。
3. 対象定義書の詳細設計を正本として、対応する実装コードとテストを、既存実装に倣って作成・更新する。
4. 実装後、**目視確認**を行う（詳細設計の論理との対応、規約適合、既存パターンとの整合）。
5. **ビルド・テスト・フォーマッタ・リンタを実行**して通過を確認する（例: `gradlew spotlessApply` / `build` / `test` / `checkstyle`）。
   - すべて通り、動作が詳細設計どおりである場合に当該工程を完了とする。
   - 失敗が生じた場合は**立ち止まり、原因を報告して指示を仰ぐ**（取り繕って強引に通さない）。
6. 続けて後述の**自己確認**を行い、全観点を満たすことを確認してから完了とする。
7. **完了時に `.codegen/progress.md` を更新する**：当該工程を `- [x]` に変え、成果物パスを記録し、本工程で生じた横断的決定（共通部品の切り出し・命名・型方針 等）・技術メモ・申し送りを各セクションへ追記する。台帳更新は完了後の事実記録であり承認ゲートの対象外（実装自体は明示許可時のみ）。あわせて、当該工程で消費した設計書（詳細設計=primary / 基本設計=supplement）の指紋を `.codegen/sources.lock.json` に記録する（`doctool hash`。次回の変更検出ベースライン）。
8. 判断に迷う点・設計や規約に無い事項は、勝手に決めずユーザーに確認する。
9. 個人情報・認証情報・シークレットはコード・テスト・ログに残さない。開発環境以外の設定値・シークレットはソースコード管理対象に含めない。

### 4.1 自己確認（実装の正本整合チェック）
実装は対象（定義書）ごとに論理を手段へ落とす作業であり、設計の取りこぼし・正本に無い挙動の混入・規約逸脱が起こりうる。
**実装後に成果物そのものを読み直し、正本（詳細設計・基本設計・実装規約）と突き合わせて整合を確かめる**ことを完了条件とする。
満たさない点があれば、勝手に取り繕わず直す（直し方が不明なら勝手に決めずユーザーに確認する）。

**観点**
- **正本に無い挙動を作らない**：実装の条件・分岐・計算は、詳細設計（および基本設計）に実在する規則だけを反映する。設計に無い仕様を推測で足さない。
- **設計の論理を取りこぼさない**：詳細設計が定める抽出条件・並び・ページング・入出力変換・分岐/異常がすべて実装に反映されている。
- **規約適合**：命名規約・レイヤ責務・共通部品の所在・例外処理の様式が実装規約に適合している。
- **再利用・重複排除**：共有要素を重複実装していない。同型ロジックは共通部品へ一元化されている。
- **提供モックアップとの視覚整合**：UI成果物がある場合、画面の構造・配色・フォント・主要寸法が提供モックアップに沿っている（採用デザイン基盤の踏襲を含む）。
- **テストの十分性**：正常系・境界値・異常系が網羅され、詳細設計の分岐・判定基準を検証している。
- **ビルド/テスト/フォーマッタ/リンタの通過**：すべて通過している。
- **秘匿情報の非混入**：個人情報・認証情報・シークレットがコード・テスト・ログに含まれていない。
