# 目的
実装済み E2E を**実行して検証**し、**受け入れ条件の充足と仕様乖離を客観的に確認**する。あわせて **testgen-exec が取得した証跡の有効性**と、**テストケース・テストコードの妥当性**を検証する。実装の修正・証跡の取得/再生成は行わない（exec の担当）。

# 引数と対象の解決
- 第1引数（必須）: **実施単位**。テストケース仕様ルート（解決は testgen-shared の実施単位・配置規範）直下の `<実施単位>/` が存在しなければ停止して確認する。未指定なら既定値を置かず、停止してユーザーに確認する。実行時の `-Pe2e.target=<実施単位>` に対応する。
- 第2引数以降（任意）: **機能名**。省略時は実施単位内の全機能を対象とする。

# 前提
- **共有規範**: Skill ツールで `testgen-shared` を読み込み、その規範（特に証跡規範）に従う。読み込めない場合は作業せず停止してユーザーに確認する。プロジェクト側に「テスト規約」ロールの上書き文書がある場合、プロジェクト固有の決定はそれが優先する。規範に無く判断できない事項はユーザーに確認する。

# 入力と成果物
- 入力：実装済み E2E、テストケース仕様、導出判断メモ、`sources.lock.json`、設計、**exec が取得した証跡一式（フレーム画像・steps.json・results.json・ビューアHTML）**
- 成果物：受け入れ確認レポート（テスト仕様書と同じディレクトリ）、検出事項（根拠付き）

# 進め方
## 1. 実行による検証
- E2E を実行し、全ケースの合否を確認する（実施単位・機能の指定はテスト規約。ArchUnit ガードレールを含む `test` も通す）。証跡の再生成は行わない。
- **不合格ケースは原因で区別して検分する**（共有規範「設計と実装の乖離の扱い」）——①**設計基準の期待結果と実装の乖離による失敗（正しい検出）**: スイートの欠陥として扱わない。exec の不具合一覧と突合し、証跡が「設計上の期待／実装の実測」の対を追跡可能に示していることを確認する。②**テスト・ハーネス側の欠陥による失敗**（セレクタ誤り・部品の誤用・データ不備等）: 是正要求として exec へ差し戻す検出事項にする。①を②と誤分類して「テストを直せ」としない・②を①と誤分類して不具合として報告しないことを検分の要点とする。

## 2. 機械突合（steps.json・全件）
フレーム画像を開く前に、機械的に照合できる整合を全件確認する（同梱ツールを使う。`scripts/check_machine.py <エビデンスdir> <仕様書ダンプtxt>`。ダンプは `scripts/dump_spec.py`、フレーム監査用のケース別分割・期待結果ダイジェストは `scripts/split_steps.py`／`scripts/make_digest.py` で作る）:
- steps.json の各ケース verify/machine 集計と results.json の合否が矛盾しないこと
- verify ステップの `frame`（と `attachFrame`）が実在すること／孤児フレームが無いこと
- 遷移部品（hidden/cleared）に**前フレーム（visible）→操作→後フレーム**が揃っていること
- 仕様書の**【機械検証】行**と machine ステップが 1:1 で対応し、期待値・実測値が記録されていること
- 連続フレーム（grid）の n/N・キー範囲が期待行数と整合すること
- 全ステップに ts があり、証跡ログと時系列で突き合わせ可能なこと

## 3. フレーム監査（実画像の検分）
**フレーム画像を実際に開いて（Read して）検分する**。全フレームをサブエージェントへ分担させ、以下を確認させる（収集と判断の分離・原文/画像事実の転記・出典必須は CLAUDE.md のサブエージェント原則に従う）:
1. 仕様書の**期待結果の各行に根拠フレームが存在するか**（可視行）。【機械検証】行はログで代替されているか
2. **キャプション（steps.json の desc/期待/実測）と画像の内容が一致するか**（例:「候補3件」のパネルに実際に3件写っているか、件名の文字列が読めるか）
3. ハイライト（赤=検証・青=操作）が**正しい要素**を指しているか
4. 画面上の **ID・値がデータ正本と突合**できるか
5. 見切れ・可読性（文字が読める倍率か）・代理証跡ラベルの明示
- メインエージェントは、検出事項・レポートに載せる主張について**該当フレームを自ら再読して確定**する（全数再読は不要、一点確認でよい）。

## 4. 受け入れ条件の充足確認
- 各ケースが受け入れ条件を満たすかを、フレーム／機械検証ログに基づき確認する。

## 5. テストケース・コードの妥当性検証
- ケースとコードの整合・同一実施単位内の不足を確認する。

## 6. 乖離・網羅・flaky の点検
- 仕様・設計との乖離、網羅（連結ビュー再生成: 全導出単位がケースID or 対象外理由を持つ）、flaky 兆候を点検する。
- **上流変更の検出**：`doctool status --lock` で突き合わせ、変更があれば「再導出要」を検出事項として報告する（基本設計⇔詳細設計のドリフト含む。是正は上流の担当）。
- **lock 自身の整合**：導出判断メモ／仕様が参照する設計書と lock のエントリの一致を確認する。

## 7. レポート
- 受け入れ確認レポートに、従来の節（実行と証跡・トレーサビリティ・上流変更/lock・網羅・flaky・検出事項・総括）に加え、**「ケース × 期待結果 × 根拠（フレーム番号 or 機械検証ログ）」のマトリクス**と**フレーム監査の結果**（検分数・不一致・見切れ等）を記載する。
- 不合格ケースがある場合は**不具合（設計と実装の乖離）一覧**の節を設け、各件に ケースNo／設計の文言（出典付き）／実測値（フレーム・steps.json 参照）／「設計と実装が一致していないための失敗」である旨を記す。是正方向（実装修正か設計修正か）の判断はユーザーに委ねる。
- 過去の実施単位を参照する場合、その証跡は当時の方式による実施記録として扱う（現行基準で不合格扱いにしない）。

# 検出事項の扱い
- 検出事項は **根拠（正本の出典＋実装/フレームの該当箇所）**を添え、**事実と解釈を区別**して報告する。
- 修正の是非・方法はユーザーに委ね、本スキルでは実装を修正しない。
