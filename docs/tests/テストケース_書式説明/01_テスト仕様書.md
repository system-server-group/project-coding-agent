# テスト仕様書 記載規範

> 共通規範は [00_共通規範.md](00_共通規範.md) を参照。本書は本様式固有の事項のみ記す。

## 役割
機能ごとの**受け入れ用テストケースの正本（本文）**。E2E テスト実装と受け入れ確認の起点であり、各ケースは設計・実装から導いた「あるべき」観点を表す。

## 配置・ファイル名
`テストケース仕様/<実施単位>/<機能>/<機能>_テスト仕様書.xlsx`。関連するデータ正本は `テストケース仕様/<実施単位>/<機能>/data/`（ベースラインは `テストケース仕様/<実施単位>/_baseline/data/`）、実行証跡は `テストケース仕様/<実施単位>/<機能>/エビデンス/` に置く（E2E テスト共通規約に従う）。

`<実施単位>`（例 `20260713_初回リリース`）は 1 回のテスト実施の単位で、仕様・データ・証跡はこの配下で一式に閉じる。**再テストは別の実施単位フォルダを起こし、対象ケースのみを載せた仕様書**を置く（ケース No は初回の番号をそのまま維持し、トレーサビリティを切らない）。

## ヘッダー固有
- 機能グループ：対象機能の基本設計「機能グループ」を転記。
- 機能名：対象機能名。

## 本文の構成と書き方（列）
| 列 | 書き方 |
| --- | --- |
| No | 手打ち採番。ケース行は `<セクション番号>-<枝番>`（機能内で一意）、セクション見出し行はセクション番号のみ（「セクションとナンバリング」参照）。トレーサビリティの軸。 |
| 正常/異常系 | `正常`／`異常`。境界値は該当する側に分類し、観点欄に「境界値」と明記する。 |
| テスト観点・シナリオ情報 | 何を確認するか。**1ケース1観点**。 |
| 前提条件 | 事前データ・ログイン状態など、実行前に成立している状態。 |
| 操作手順 | 画面操作を番号付きで（再現可能な粒度）。 |
| 期待する結果 | **画面から観測できる挙動**で、合否を一意に判定できるように書く。 |
| 参照テストデータ・期待値 | 依拠するデータ正本（csv 等）・期待値の所在。パスは**実施単位からの相対**（`<機能>/data/…`／`_baseline/data/…`）で書き、実施単位名は含めない。無ければ空。 |
| 合否 | 実施時に記入する受け入れ記入欄。 |
| 発生事象・再現方法 | 不合格時の事象・再現手順。受け入れ記入欄。 |

## セクションとナンバリング
- 本文は**類似のテスト観点ごとにセクション**を切る。本文は次の2種類の行で構成する。
  - **セクション見出し行**：No 列にセクション番号（1始まりの整数連番）、観点列以降（B〜I）を**結合**してセクション名を記載する。セクション名は観点のまとまり（例：画面仕様・画面イベント処理／サーバー・APIサービス（イベント処理）／入力チェック関連）を表す。
  - **ケース行**：No は `<セクション番号>-<枝番>`。枝番はセクション内で1始まりの連番。
- ケース No は機能内で一意であり、トレーサビリティ（E2E テスト表示名・証跡・results.json）の軸は**この `n-m` 形式の No** とする。セクション見出し行はトレーサビリティの対象外（ケースではない）。
- セクションの区分は**観点カタログ**（[02_テスト観点カタログ.md](02_テスト観点カタログ.md)）を標準とし、機能間でむやみに増やさない。

## 検証層の表記
- 入力チェックの検証層は**サーバー検証を既定**とし、既定の場合は表記しない（期待結果はサーバー検証の観測＝再表示・メッセージ・未登録で書く）。
- クライアント検証固有の挙動を確認するケースは、テスト観点・シナリオ情報の先頭に**【クライアント検証】**と明記する（【境界値】と同様のタグ表記）。

## トレーサビリティ
- `設計項目 ↔ No ↔ E2Eテスト ↔ 実行証跡` をケース No（`n-m` 形式）で連結する。
- **E2E テストの識別・表示名はケース No に一致**させ、証跡が各ケースへ 1:1 で辿れるようにする。
