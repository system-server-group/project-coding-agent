# 目的
**plan で（ケース本文＋入力データ＋期待値まで）完成済みの**テストケース仕様を正本として、対応する **E2Eテストを実装・実行し、証跡（コマ送りフレーム＋steps.json）を取得する**。ケースの作成・入力データや期待値の新規作成・変更は行わない（testgen-plan の担当）。データ由来オラクルの母集団・期待値が確定していない仕様は未完成とみなし、実装に進まず**立ち止まって報告**する。

# 引数と対象の解決
- 第1引数（必須）: **実施単位**。テストケース仕様ルート（解決は testgen-shared の実施単位・配置規範）直下の `<実施単位>/` が存在しなければ停止して確認する（実施単位の新設・仕様の用意は testgen-plan の担当）。未指定なら既定値を置かず、停止してユーザーに確認する。実行時の `-Pe2e.target=<実施単位>` に対応する。
- 第2引数以降（任意）: **機能名**。省略時は実施単位内の全機能（`-Pe2e.features` に対応。粒度は機能まで）。選択外の機能のテストクラスは**コンテキスト起動前に**無効化され、アプリ・DBコンテナを起動せずスキップされる（`@E2eFeature` 注釈＋`E2eFeatureSelection`）。

# 前提
- **共有規範**: Skill ツールで `testgen-shared` を読み込み、その規範（特に証跡規範・実行ハーネス規範）に従う。読み込めない場合は作業せず停止してユーザーに確認する。プロジェクト側に「テスト規約」ロールの上書き文書がある場合、プロジェクト固有の決定はそれが優先する。規範に無く判断できない事項はユーザーに確認する。

# 入力と成果物
- 入力：承認済みテストケース仕様、データ正本、設計（視覚はモックアップ）、既存のE2E実装・検証部品
- 成果物：E2Eテスト（Page Object＋検証部品によるシナリオ）と、実行で得る証跡一式（フレーム画像・steps.json・results.json・ビューアHTML・動画webm・デバッグ補助のtrace）

# 実装の方針
## 層分けと検証部品（最重要）
- 画面の構造（要素の指定・操作）は **Page Object** に閉じ込め、シナリオには**意図だけ**を書く。**Page Object の役割はロケータの提供と操作のみ**——DOM から読み取った値を返して検証材料にしない（読取・期待値との突合・記録は部品の仕事）。操作に付随する読取（ドラッグ座標の `boundingBox`・冪等判定の `count` 等）は可。
- **検証・操作フレームは `E2eVerify` 部品経由のみ**。素の Playwright/JUnit アサーション・DOM 読取の直呼びは禁止（テストクラスに `@EvidenceV2` を付与し、ArchUnit `EvidenceV2GuardrailTest` が通常 `test` タスクで構造的に強制する。テストクラスは読取全面禁止、Page Object・糊クラス等のキット外は `@E2eRawDom(対応先)` を付けたメソッドに限り `evaluate` 等の生 DOM アクセス可）。
- **`@E2eRawDom` を付与できる条件**: 仕様書で【機械検証】と宣言された期待結果の実測、または仕様書に明記されたバイパス手順・合成操作に対応する場合のみ。value に対応先を記し、**完了報告で付与メソッドの一覧を報告**する。
- **部品不足時は停止する（代替実装の禁止）**: 部品で表現できない検証に出会ったら、実装を進めず**停止して「部品不足」として報告**し、部品追加（キット `harness/` への追加＝ユーザー合意の上でキット保守として実施し、転写・再実行する）を提案する。テスト・Page Object 側での代替——スクロールしながらの撮影ループ、DOM 読取値の `machineEquals` 転記、検証対象と無関係な要素を target にした流用——は**禁止**。
- **キャプション（desc）はアサーションと一致させる**: フレームの desc が主張してよいのは、そのステップのアサーションが実際に検証している事実だけ（証跡規範）。アサーションが検証しない事柄（周辺の表示・範囲の網羅）を desc の文言で主張しない。
- **`machineEquals` は仕様書で【機械検証】と宣言された期待結果に限る**。可視で確認できる期待結果を機械検証で代替しない（部品が規格の一部として内部記録する機械ステップはこの限りではない）。

## 部品カタログ（`verify.*`）
| 部品 | 用途 |
|---|---|
| `op(desc, action[, target])` / `opFrame(desc[, target])` | 入力系の操作＋フレーム。target は**操作で値・状態が変化した要素**（入力した欄・選択したファイル名の表示先・追加された行 等）に限り指定する（reveal＋見切れ検査＋青ハイライト）。**画面を開く操作に target を流用しない**（読込完了の目印は不可。desc に「アドレスバー」を含む target 指定は部品が拒否する） 。複合操作は観測可能な変化ごとに分割する |
| `opOpen(desc, action)` | **画面を開く・URL直打ち・リロード**の操作フレーム（target なし・青ハイライトなし）。遷移の事実は情報バーの URL・証跡ログ（NAV）に残り、到達した画面の正しさは後続の検証（`urlIs`・画面タイトル等）で受ける |
| `opPress(desc, control, action[, target])` | **押下系**（画面遷移・画面の作り替えを起こす操作）。押下前に操作対象（control）を青ハイライトで1枚＋押下後に結果を1枚＝**操作の再現性**。実クリックを伴わない合成送信（requestSubmit 等）には使わない（op のまま） |
| `opPressWithInput(desc, input, control, press[, target])` | **入力を伴う押下系の複合操作**（仕様書が「…を入力し「ログイン」を押下する」を1手順で記す型）。入力を実行してから押下前フレームを撮るため、押下時点の入力値がフレームに写る（`opPress` に入力までまとめて渡すと押下前フレームが未入力のまま撮られ、キャプションと画像が不一致になる）。入力の結果が押下対象と別画角に現れる複合操作は従来どおり `op` で分割 |
| `visible / text / texts / containsText / value / checked / unchecked / countIs / disabled` | 単体の可視検証（reveal＋見切れ検査＋赤ハイライト＋フレーム）。`countIs` は 1 件以上のみ（0 件指定は部品が拒否——「無いこと」は `absent`） |
| `absent` | 要素が**無いこと**の検証（初期状態の不在の一般解）。無いことの文脈を示す実在要素（アンカー）を可視検証して**破線枠＋ラベルで図示**し、その文脈で対象が 0 件であることを機械検証する。CSS 非表示は target 側の `:visible` フィルタで受ける。操作による消失は transition 部品（前後フレーム必須） |
| `textTruncated` | 表示内容が要素幅に収まらない**切り詰め（CSS の省略表現）**の検証。省略表現は描画のみで DOM テキストは全文のまま（`text` 等では検証不能）のため、内容幅>要素幅の実測を規格内の機械記録として残し、見た目はハイライト＋フレームで受ける。対象要素は描画済みであること（仮想化列は `gridCellText` 等で画面内へ入れてから） |
| `positionedAbove` | 対象が基準要素の**上方向に配置**されていることの検証（`textTruncated` と同型——見た目は両要素のハイライト＋フレームで受け、位置（対象の下端 ≦ 基準の上端）の実測を規格内の機械記録として残す）。ページをスクロールしないため、対象・基準が画面内にある画角を作ってから呼ぶ（ポップアップ型の対象はページスクロールで閉じるため） |
| `sameText` | 対象が基準要素と**同じテキスト**を表示していることの検証（`positionedAbove` と同型——見た目は両要素のハイライト＋フレームで受け、両要素の実測テキストとその一致を規格内の機械記録として残す）。「更新日時は登録日時と同じ値」等、**期待値が実行時にしか確定しない値の要素間比較**に用いる（固定の期待値と突合できる場合は `text`）。複合表示（例「{登録者}({部署}) – {日時}」）から比較部分を取り出す場合は抽出正規表現付きオーバーロードを使う。部品は両要素が同一画角に収まるようスクロールを調整してから見切れ検査を行う（外接範囲が1画角に収まらない配置は見切れの失敗として記録） |
| `urlIs` | URL検証（情報バーに写る）。遷移の事実は証跡ログ（NAV）にも自動記録される |
| `transitionHide / transitionCleared`（＋`ByPress`／`ByConfirm`） | 表示→操作→非表示/消去。**前後フレーム必須**・消えた領域を破線ゴーストで示す。削除で**別の要素が旧位置へ流入した場合は機械判定**（祖先コンテナの背景は「空」扱い）し、ゴーストのラベルに明示＋note に流入要素の識別情報（タグ・class・先頭テキスト）を記録。confirm 付き削除は `transitionClearedByConfirm`（代理証跡パネル＋本文機械検証を内包・応答は常に承認） |
| `autocompleteOptions` | datalist候補（ネイティブUIは写らないため代理証跡パネル＋機械検証）。**候補が多い場合は Path オーバーロード（期待値正本CSV）**を使う＝パネルは先頭10件＋「全件を正本と機械突合」の注記になる |
| `selectOptions` | **select 要素の選択肢**の検証（`autocompleteOptions` の select 版・同じ規格）。ネイティブのドロップダウンは写らないため、DOM 上の option の表示ラベルを代理証跡パネル＋機械突合で受ける。空欄の選択肢は空文字として期待に含める |
| `csvDownloaded` | DL内容（DL実物の先頭行を代理証跡パネル表示＋ファイル名・バイト一致・SHA-256 を機械検証。パネルに載らない行がある場合は省略の脚注＝先頭N行のみ表示・全行を機械突合を明記）。**DL実物を証跡として保存**しビューアから開ける（`No.<No>_<連番>d_<名前>`） |
| `noDownload` | 操作の後にファイルの**ダウンロードが発生しないこと**の否定観測（`noMailSent` と同型。2秒観測・フレーム無しの【機械検証】）。操作の結果（遷移先等）は後続の可視検証で受ける |
| `listVisibleCount` | 非仮想化リストで、スクロールコンテナの可視領域に**完全に収まって表示されるアイテム数**の検証（「一度に表示される件数は N 件」型）。可視アイテムのハイライト＋フレームで受け、件数の実測を規格内の機械記録に残す |
| `listItemsByText` | 非仮想化リスト（オートコンプリート候補等）の**縦**スクロール連続フレーム（重複2件・アイテムテキスト必写・n/N記録・末尾で件数の締め）。`gridRowsByKey` と同じ規格のリスト版で、アダプタ不要（スクロールコンテナ＋アイテムの2ロケータを渡す）。ポップアップ型のリストは開く前に画角を作ってから（部品はコンテナ内部のみスクロールする） |
| `gridRowsByKey` | 仮想化グリッドの**縦**スクロール連続フレーム（重複2行・行キー必写・n/N記録）。末尾で**行数の締め**（期待件数の次の行が無いこと＝余剰行の不在）を機械検証。グリッド構造は `E2eGridAdapter` で渡す |
| `gridColumnHeaders` | 仮想化グリッドの列ヘッダーを**横**スクロール連続フレームで検証。各フレームで完全可視の列すべてを期待順と web-first で突合し**全列ハイライト**（バッジは**固定列を含む全列の列順の番号**でフィルム全体を通して1→Nへ一度だけ進む——固定列1..Pは**最初のフレームのみ**番号・以降は枠のみ。隣接フレームの重複列は同番号で継ぎ目を示す。列順確認に固有の採番）・直前フレームと1列重複・キャプションに n/N と列範囲・固定列は毎フレーム検証・事前走査の全列突合と被覆を機械記録。窓より幅の広い列は単独フレーム＋要素単体ショット |
| `gridCellText` | 仮想化で DOM に無い列のセル検証。部品が横スクロールで列を描画・ヘッダー窓へ寄せてから通常の可視検証（reveal＋見切れ検査＋赤ハイライト＋フレーム） |
| `gridColumnNumericDescending` | グリッド1列の値が**数値として降順**であることの機械検証（仕様書の【機械検証】行と対応。値の列と判定を steps.json へ記録。行仮想化のため全行が描画されている状態で用いる） |
| `gridColumnWidthIs` | グリッド1列の**実測幅**の検証（仕様書の【機械検証】行と対応。`positionedAbove`・`textTruncated` と同型——見た目は対象列ヘッダーのハイライト＋フレームで受け、実測幅（ヘッダーセルの描画幅・px）の一致を規格内の機械記録として残す）。リサイズ操作（`resizeColumnTo` 等）やレイアウト復元の結果検証に用いる。対象列のヘッダーが描画されている状態で呼ぶ |
| `mailReceived / noMailSent` | 受信箱（MailHog Web UI）を開いて映す＋API待機は機械記録。`noMailSent` の不在検証は受信一覧ツールバー（0件でも実在）を文脈アンカーにする（MailHog の内容ペインは Page Object が情報バー分オフセットして見切れ検査を満たす画角にする） |
| `mailBodyLineShown` | 表示中メールの本文から**正規表現に一致する行**を本文ペインの内部スクロールで画角へ入れ、一致範囲を赤枠ハイライトしたフレームで**可視検証**（一致内容と画角判定は規格内の機械記録）。長い本文はペイン内部でスクロールし要素単位の見切れ検査では下部の行が写らないため、本文下部の行（【登録日時】等）の可視宣言はこの部品で受ける。空欄の行は「ラベルの後が行末まで空」の一致（例 `^【商流】 *$`）として行ごと映す。事前に `mailReceived` 等で対象メールを表示していること（正規表現は MULTILINE で適用） |
| `mailBodyItemNamesAre` | メール本文の**項目名（各行頭の【…】）の並び**を期待リストと機械突合（テンプレートの項目名・並びの検証）。先頭サンプルの代理証跡パネル＋全件機械突合の規格。対象は最後に受信したメール |
| `mailBodyNotContains` | メール本文に指定文字列が**含まれないこと**（0件）の機械検証（不含有は受信箱 UI の可視では受けられないため。フレーム無し） |
| `machineEquals` | 画面に出ない検証。**仕様書の【機械検証】行と 1:1 対応させる**（可視期待結果の代替禁止）。実測値を steps.json へ |
| `captureResponse`＋`responseStatusIs / responseBodyEmpty / responseErrorsAre / responseBodyExcludes / responseNotRedirected` | **HTTP 応答の機械検証**（「HTTP応答が NNN」「ボディなし」「errors 配列」「内部情報を含まない」「リダイレクトが発生していない」型の【機械検証】に対応）。`captureResponse` が操作（`opPress`・`opOpen` 等の部品呼び出しを渡す）の実行中にメソッド＋URL部分一致の応答を捕捉して不透明ハンドルを返し、検証部品がそれを消費する（捕捉・検証ともフレーム無しの機械記録。ハンドルの生読取・`machineEquals` への転記はしない） |
| `noRequestSent` | 指定の HTTP 要求が**送信されないこと**の否定観測（「登録の要求が送信されていない」等の不呼出の期待。証跡規範7）。操作＋2秒観測・フレーム無しの【機械検証】 |
| `opBypassRemoveAttribute / opBypassSetAttribute` | **サーバー検証バイパス**の合成操作（maxlength 解除・type 変更等。仕様書のバイパス手順に対応）。フレームは撮らず、属性の変更前後を【機械検証】で記録 |
| `opInsertSpacerAbove` | ポップアップ型部品の**配置検証の画角**を作る合成操作。対象要素の直前に指定高さの余白要素を挿入し、上方向の領域を決定的に確保する（対象の上にコンテンツが少ない画面ではスクロールで画角を作れないため。開発者ツール相当・手段1の系）。フレームは撮らず、挿入した余白の実高を【機械検証】で記録（作られた画角は後続の操作フレームで受ける） |
| `opDropFolder` | ドロップ領域へ**フォルダ**をドロップする合成操作。OS のファイルマネージャからのドラッグは再現できず、フォルダを表す `DataTransfer`（`items[0].webkitGetAsEntry()` がディレクトリを返す）もブラウザ API から組み立てられないため、`files`＋ディレクトリを返す `items` を備えた `drop` を合成して発火する。結果は画面に出るため操作フレームを撮り、合成入力（ディレクトリ判定・添付件数・フォルダ名）を【機械検証】で記録 |
| `opDropFile` | ドロップ領域へ**ファイル**をドロップする合成操作（`opDropFolder` のファイル版）。実ファイルの内容を積んだ `File` を持つ `drop` を合成発火する（内容は Base64 でページへ渡すため、大きいファイルは `opChooseFile` を使う）。結果は操作フレームで撮り、合成入力（ファイル判定・件数・名前・バイト数）を【機械検証】で記録 |
| `opChooseFile` | **ファイル選択ダイアログ**を開く操作でファイルを1件指定する合成操作。ダイアログは撮影に写らないため FileChooser で受けてファイルを設定し、結果（選択されたファイル名の表示等）は操作フレームで撮る。input へ設定されたファイル名・実バイト数を【機械検証】で記録。**選択がアプリ側で却下される（解除される）ことを期待するケースには使えない**（保持の機械検証が必ず失敗する）——`opChooseFileRejected` を使う |
| `opChooseFileRejected` | ファイル選択が**アプリ側で却下される**（形式チェック違反等で選択が解除される）ことを期待するケースのファイル選択操作。保持の検証を行わず、ダイアログへの入力（指定した実ファイルの名前）を `opChooseFileSubmits` と同じ規格で機械記録するに留める。却下の効果（エラーメッセージ・選択済みファイル名が表示されないこと等）は後続の検証で受ける |
| `opPressConfirm` | **ネイティブ confirm ダイアログ**を伴う押下（削除確認等）。ダイアログは撮影に写らず既定では自動キャンセルされるため、部品が本文を捕捉して OK／キャンセルを応答し、**本文・応答の代理証跡パネル＋本文一致の【機械検証】**を押下前後フレームとともに記録 |
| `openOtherBrowser`（基底クラス） | **別ブラウザ（別セッション）**を開く（排他制御・「読込後に他ユーザが更新した」状態の再現）。主ブラウザと同じ steps.json へ連番記録する専用 verify を返し、1本のフィルムストリップで「誰がいつ何をしたか」を追える（動画は主ブラウザのみ・ケース終了時に自動クローズ） |
| `opArmFault / faultFired` | **障害シーム**の有効化（画面に写らない合成操作。有効化を【機械検証】で記録）と、対象操作後の発火の機械検証。シーム Bean 側は `E2eFaultSeams.shouldFire(シーム名)` で判定する（発火後自動解除・ベースラインリセット時に全解除）。シーム名は仕様書の操作手順の記載と一致させる |

- **グリッド部品はアダプタ経由**: グリッド構造（スクロールコンテナ・セル・ヘッダー）は `E2eGridAdapter` が供給する。ag-grid はキット同梱の `E2eAgGridAdapter` を Page Object から生成して部品へ渡す。別のグリッドライブラリはアダプタをプロジェクト側（`testgen.e2e` 配下）で実装する。アダプタは**ロケータの供給とグリッド固有のドラッグ操作（列幅変更・列順変更）**を担い、DOM の値を読み取って返さない。
- **列幅の変更・最小幅への到達・列順変更（列ヘッダーの D&D）はアダプタの操作 API を使う**（`resizeColumnBy` / `resizeColumnTo` / `shrinkColumnToMinimum` / `moveColumn`）。**`page.mouse()` によるリサイズ・列移動ドラッグの手組みは禁止**。ドラッグイベントの解釈はグリッドライブラリの内部仕様（ag-grid は minWidth 未満の要求幅の mousemove を丸めずに棄却し、mouseup でも下限へスナップしない。列移動はドラッグ開始しきい値とポインタ位置・移動方向からの挿入位置計算を持つ）に依存し、手組みは開始幅・移動刻みに依存する非決定な結果を生むため（機構の詳細は `E2eAgGridAdapter` の注記）。`moveColumn` の契約は「ドロップ先列ヘッダーの中心で離す」まで——移動可否（移動不可列・固定領域）と挿入位置の解釈はライブラリの挙動に委ね、並び替えの結果は `gridColumnHeaders` 等の検証部品で受ける。
- ビューポートより大きい要素は部品が**要素単体ショット**（`..a.jpg`）を自動添付する。
- **要素が存在しない失敗も証跡に残る**: 検証対象・操作対象・押下対象・列などが画面に存在しない場合（設計と実装の乖離の典型）、部品が短い待機（5秒目安）の後に**現画面のフレームと期待／実測の対（または fail の操作ステップ）を記録してから失敗**させる。長い既定タイムアウトの無記録エラーにはならないため、この種の失敗はそのまま不具合一覧の根拠にできる。
- **効果が後続フレームで可視にならない合成操作**（Cookie削除等）は、直後に効果の実測を `machineEquals` で記録する（例: 削除後のCookie件数=0）。
- **障害系（ロールバック・内部エラー・送信失敗・競合検出等）の再現は、テストプロファイル限定の委譲シーム Bean**で行う（機能対応物として本スキルが作る。アプリの Bean を委譲でラップし、障害を注入する分岐で `E2eFaultSeams.shouldFire(シーム名)` を呼ぶ）。状態管理（ケース単位トグル・発火後自動解除・ベースラインリセット時に全解除）と発火記録はキットの `E2eFaultSeams` が担い、テスト側は `opArmFault`（有効化）→対象操作→`faultFired`（発火の機械検証）で受ける。手段の使い分けは testgen-shared「到達手段カタログ」に従う。外部コンテナの停止・ネットワーク断・時間経過待ちによる再現は用いない（非決定的なため）。
- 既存の Page Object・補助を再利用し、2箇所以上で同型になるものは共通化する。セレクタは壊れにくい指定（役割・ラベル等）を優先し、命名・配置は既存のテスト資産に倣う。

## データと冪等性
- ベースラインは規約の仕組みで用意し、実行前にリセットする。更新系シナリオは自己完結させる。
- 仕様が参照するテストデータは**実在・解決可能であることを確認**してから実装する。参照先が未整備なら立ち止まって報告する（正本は勝手に作らない）。
- 仕様書が「テスト実行時に生成」と定めるファイル・フォルダ（長名境界等）は、テストコードが一時ディレクトリへ仕様書の指定どおりの名前・内容で生成して用いる（リポジトリのデータ正本には置かない）。

# 進め方（工程単位・承認ゲート）
0. **着手時の変更検出**：実施単位フォルダ直下の `sources.lock.json` を `doctool status --lock` で突き合わせ、上流（設計）が変わっていれば testgen-plan の再導出が要るとして**立ち止まって報告**する。あわせて仕様の整合と承認基準線を突合する——`PYTHONUTF8=1 python .claude/skills/testgen-plan/scripts/spec_integrity/spec_integrity.py check <実施単位dir>`（testgen-plan 同梱）。整合エラーまたは**要裁定差分**（承認後の人手変更＝ケースの追加・削除・改変。合否等の人の記入欄は検出対象外）があれば実装・実行に進まず、差分一覧を提示して**変更した理由を人に確認**する。裁定の記帳（実施単位直下 `ケース変更台帳.md`）と基準線更新（同スクリプト `lock`）はスキルが代行し、完了後に再開する（exec は裁定しない——採用/差戻しの判断は人、仕様の編集が必要なら testgen-plan）。
1. 対象のテストケース仕様とデータを読み、シナリオと期待結果（可視／【機械検証】の別を含む）を把握する。
2. 実装方針・影響範囲・リスクを説明し合意を得る。
3. Page Object／シナリオ（部品呼び出し）を作成・更新する（既存実装があればそれに倣う。対象機能の実装が無い状態からの新規作成が通常形）。
4. 実装後、目視確認と実行確認（証跡取得）を行う。失敗の原因を切り分ける——**テスト・ハーネス側の欠陥**（セレクタ誤り・部品の誤用・データ不備・環境起因等）は是正して再実行する。**設計基準の期待結果と実装の乖離による失敗は是正対象ではなく検出結果**であり、失敗のまま残す（共有規範「設計と実装の乖離の扱い」）。
5. **設計・仕様と実装の乖離を見つけても、期待値を実装へ寄せない・是正方向の確認を取らない**。テストは仕様書どおりに実装・実行し、乖離はテストの失敗として検出する。**正本（仕様書）は勝手に書き換えない**。ただし**到達と検証を区別する**——画面への到達・要素の特定（ロケータ）は実装の実状に従ってよい。設計上の文言だけでロケータを書くとセレクタ待ちのエラーになり証跡が濁るため、実装の実状で対象へ到達し、文言・挙動の正しさは検証ステップで設計基準に落とす（失敗が「期待/実測」の対として綺麗に steps.json・フレームに残る）。仕様書の操作手順自体が実装上実行不能な場合（画面・部品が存在しない等）は、到達できた最初の検証ステップの失敗として検出し、後続の期待結果は「この不具合により未到達」と報告する。
6. 実行後、失敗ケースを**不具合一覧**として報告する——各件に: ケースNo／設計の文言（出典付き）／実測値（steps.json・フレーム参照）／「設計と実装が一致していないための失敗」である旨。仕様書の合否・発生事象欄は人の受け入れ記入欄のため記入しない。是正方向（実装修正か設計修正か）の判断はユーザーに委ねる。

**ファイルの生成・編集は、直前のユーザー発言に明示の許可がある時のみ行う。**
個人情報・認証情報・シークレットを spec・csv・証跡・ログに残さない（開発環境専用のダミー値のみ）。

# テスト実施単位
仕様・データ・ベースライン・証跡は**実施単位**ごとに一式で閉じる（詳細はテスト規約）。実行は `-Pe2e.target=<実施単位>` 必須・`-Pe2e.features=` で機能単位まで絞れる（ケース単位不可）。ケース・実装に変更が無ければ、exec は**コード変更なしで実行と証跡取得のみ**を行う（配置は `-Pe2e.target` から解決され、テストコードは実施単位名を持たない）。

# 証跡の生成
`e2eEvidence` タスク（slowMo 既定 500ms）で実行すると、機能ごとの証跡フォルダへ以下が出力される。

- フレーム `No.<ケースNo>_<連番2桁>.jpg`（ケース開始時に同ケースの旧フレーム・旧DL実物は洗い替え）／要素単体ショット `..a.jpg`／DL実物 `No.<ケースNo>_<連番2桁>d_<元ファイル名>`
- `steps.json`（操作・検証ステップ＝キャプション・期待/実測・ハイライト矩形・時刻、および**証跡ログ**＝NAV/操作/検証イベント＋アプリlogback＋ブラウザコンソール(自アプリのwarning/error)）
- `results.json`（ケース単位の機械判定）
- 動画 `.webm`（証跡として管理対象）・トレース `.trace.zip`（デバッグ補助・VCS管理外）

後段タスク `e2eEvidenceIndex` が受け入れ用ビューア——**サマリ `index.html`＋ケース別 `case-<No>.html`**（フィルムストリップ・全体フィット＋ホイールズーム・証跡ログ・仕様書本文併記）——を生成する。**ビューアは正本（xlsx＋steps.json＋results.json＋証跡）からの再生成物**であり手編集しない。

## 同梱ツール（ビューア生成）
生成スクリプトは本スキルに同梱（`scripts/e2e_evidence/e2e_evidence_index.py`）。**呼び出しは転写した `testgen.e2e.gradle.kts` のビルドタスク経由**（仕様ルート等を引数で渡す）。対象はテスト実行と同じ指定から決まる。`steps.json` が参照するフレームの欠落は生成失敗（＝ビルド失敗）。steps.json の無い過去実施単位は従来レイアウトで後方互換生成される。

# ハーネス契約（キットの転写）
E2E ハーネス（基底クラス・検証部品・記録・配置解決・ガードレール・メール補助・シード支援）の正本は**本スキル同梱のキット `harness/`**（構成と転写手順は `harness/README.md`）。**キットは中立パッケージ `testgen.e2e.support` で書かれ、プロジェクトの機能にも固有識別子にも依存しない**（保守は testgen-shared「保守・可搬性の規律」に従う）。

- プロジェクトに E2E ハーネスが無ければ、Java 一式を `src/test/java/testgen/e2e/support/` へ**無改変で**転写し、Gradle 設定 `testgen.e2e.gradle.kts` をプロジェクトルート直下へ転写して `build.gradle.kts` に `apply(from = "testgen.e2e.gradle.kts")` を 1 行追記する（E2E 専用依存・タスクはこのスクリプトが持ち、プロジェクトのビルドスクリプトへ直接は足さない）。プロジェクト適合は**糊クラスの生成**（`testgen.e2e.ProjectE2eTest`。アプリ起動クラス・Testcontainers 設定・アプリのルートパッケージを供給する。雛形は `harness/README.md`）と、`// [PROJECT]` マーカー箇所（ビューア生成スクリプトのパス）のみ。**キット本体は書き換えない**。E2E テストコード（糊クラス・シーダー・Page Object・テストクラス）は全て `testgen.e2e` 配下に置く。転写後にコンパイルが通ることを確認する。
- 転写済みハーネスが既に在る場合は、着手時にキットと突合（diff）し、差分があれば乖離として報告して立ち止まる（正本はキット。転写物側の手直しで吸収しない）。差分の原因が**キット側の更新**である場合は、キットを正として**再転写**し、部品シグネチャ変更の影響（コンパイル不能となる既存テスト・置換が必要な部品呼び出し）を一覧にして報告し、合意の上でテスト側を改修する。
- 転写時、VCS 設定を testgen-shared「実施単位・配置規範」の VCS 整備の定めに従い整備する（無ければ追記）。
- **糊クラス・機能対応物はキットに含まれず、本スキルが作る**: 糊クラス（`ProjectE2eTest`）・シーダー（`E2eBaseTest.resetBaseline()` の実装。`E2eSeedSupport` の parseCsv／requireHeader／parseSeedId／moveSequencePastSeedBand を使い、列はテーブル定義に一致させる。自動採番の列も CSV に明示し `OVERRIDING SYSTEM VALUE` で投入する。シード帯域の上限は既定 `SEED_ID_MAX`＝1000。仕様が異なる帯域を契約している場合は糊クラス等に有効値を定義し、parseSeedId と moveSequencePastSeedBand の両方へ同じ値を渡す）・Page Object・テストクラス・障害シーム。テストクラスには対象機能を **`@E2eFeature("<機能フォルダ名>")`** で宣言する（機能絞り込みがコンテキスト起動前にこの注釈で判定する。`featureName()` は注釈を読む final メソッドでありオーバーライド不可）。

- 表示名にケース No（`No.<ケースNo>`）を含める（仕様書と一致。証跡・steps.json・results.json の対応キー）。
- 標準フレームは固定ビューポート（1280×800）。シナリオ途中でビューポートを変更しない。全体撮影は行わない。
- オーバーレイ（情報バー）: URL・入力値（checkbox/radio は ON/OFF、file はファイル名）・現在ステップ名を表示。クリック波紋・マウスドット併用。値は開発用ダミーのみ。
- 機械判定は `results.json`、ステップと証跡ログは `steps.json`。失敗テストでも中断時点までのステップが残る。

# トレーサビリティ
`受け入れ条件 ↔ ケースID ↔ 設計項目 ↔ E2Eテスト ↔ フレーム/steps.json` を連結する。テストの表示名は仕様書のケース番号に一致させ、各期待結果が**根拠フレーム（または【機械検証】のログ）へ 1:1 で辿れる**ようにする。

# 完了条件・自己確認
- 仕様の全シナリオが部品で実装され、`test`（ArchUnit ガードレール含む）が通り、`e2eEvidence` が**完走して全ケースの証跡が取得されている**（`e2eEvidenceIndex` は finalizer のため検証失敗があってもビューアまで生成される）。
- **全ケース合格は完了条件ではない**。設計基準の期待結果と実装の乖離による失敗は検出結果であり、不具合一覧（進め方6）として設計の文言・実測値の対で報告されていること。テスト・ハーネス側の欠陥による失敗が残っていないこと。
- 各ケースの期待結果に根拠フレームまたは【機械検証】ログが対応している（見切れ検査は部品が機械強制。失敗ケースも失敗時点までのフレーム・ステップが残る）。
