# 実装（コード生成）共通規範

> 本書は詳細設計から**コードを生成・実装する際**に共通する規範を定める。設計書（様式）の記載規範
> （**詳細設計書 共通記載規範**および各様式の記載規範）とは別系統で、**実装手段（言語・フレームワーク）に踏み込む規範**をここに集約する。
> 各様式の記載規範（言語非依存）は **詳細設計書 共通記載規範** を正本とし、本書はそれを侵さない。

## 位置づけ
- 設計書（記載規範）は「言語固有のメソッド名・型名を書かない」方針のため、共通部品化など**実装レベルの判断**を表現できない。
- その結果、コード生成では同種ロジック（例：区分コードの解決）が機能・型ごとに重複生成されやすい。
- 本書はその重複を防ぐ**実装側の正本**として、横断的に適用する規範と共通部品の所在を定める。

## 改善の取り込み
生成はセッション間で記憶を持たないため、改善を次回生成へ確実に引き継ぐ仕組みを本書群で担う。

- 生成結果に**重複・規約逸脱・設計ドリフト**を見つけたら、その場の修正で終わらせず、次の2つを必ず行う:
  1. 横断的に再利用できるロジックは**共通部品へ一元化**する（下記「共通部品の所在」）。
  2. 再発防止の判断を**本書群へ規範として追記**する（様式別の事項は様式別ファイルへ）。
- 規範の**正本は本書群（バージョン管理下）**。自由記述の備忘録は作らない（ドリフトの原因になる）。
- 追記は「何を・なぜ」を一文添える程度に留め、判断が追えるようにする。

## バージョン依存の固有名（記憶で書かない）
- 言語・フレームワークのバージョンで変わる固有名（注釈・型・メソッド名等）は、**記憶（既定の思い込み）で書かず、`build.gradle.kts`（版の正本）で版を確認し、当該版の API に従って確定する**。
- 規約・コードには**当該版で正しい名称を1つだけ**書く。旧版の名称や移行の比較（「旧称は〜」「別版では〜」）は本文に書かない（誤名称の再混入＝ドリフトの媒介になるため）。

## 再利用・重複排除（DRY）
- **横断的に再利用されるロジックは共通部品として一元化し、機能・型ごとに重複実装しない。**
- 2 箇所以上で同型の実装が現れたら、共通部品へ切り出してから各所を委譲に置き換える。
- 汎化により見通しが良くなる場合のみ切り出す。1 箇所限定・将来再利用が見込めないものは無理に共通化しない。

## 共通部品の所在
- 横断ユーティリティ・共通インターフェースは `com.system_server.ai_demo.commons` 配下に**種類別のサブパッケージ**で置く（ハンドラ・列挙型基盤・ユーティリティ等を未分類で混在させない）。
  - `commons.code`：区分（列挙型）の共通基盤（`CodeEnum`／`CodeEnums`／`CodeEnumSerializer`）。
  - `commons.error`：API 共通エラー応答（`ApiExceptionHandler`／`ErrorResponse`／`ErrorItem`）。
  - `commons.validation`：システム共通の入力値チェック（`DateInBounds`／`DateRange` 等）と共通メッセージ（`CheckMessages`）。
  - `commons.web`：Web 入出力境界の共通変換部品（`IsoLocalDateEditor`）。
- 特定機能に依存する実装を commons に置かない（依存方向は「機能 → commons」の一方向）。**機能固有の値（項目名・項目順など）を共通クラスに焼き込まない。**

## レイヤ責務
**詳細設計書 共通記載規範**「レイヤ責務・設計方針」を実装に落とす際の補足。

- レコード ⇄ ドメイン型の変換は**サービス層**で行う。区分コード → 列挙型の変換もここで共通部品を用いて行う。
- コントローラーは入力チェックとサービス委譲に徹し、変換・業務ロジックを持たない。
- データアクセス（Mapper）は 1 表専用。
