# API定義書 記載規範

> 共通規範は [00_共通規範.md](00_共通規範.md) を参照。本書は本様式固有の事項のみ記す。

## 役割
JSON を返すコントローラー（クラス）**1件**の定義。配下に**複数のAPI**を持つ（公開API一覧）。

## 配置・ファイル名
`イベント定義書/コントローラー定義書/<機能>[_<アクション>]_API定義書.docx`（API定義書・画面コントローラー定義書はフラット同居）。

## ヘッダー固有
- 機能グループ：対象機能の所属グループ（基本設計ヘッダーから転記）。
- 機能：`<機能名> / <コントローラー論理名>`（2段落）。

## 本文の構成と書き方
- **コントローラー基本情報**：論理名／物理名（`～Ctrl`）／ベースパス（`/api/...`）／処理内容。
- **公開API一覧**（APIごとに以下を繰り返す）：
  - **API基本情報**：論理名／物理名（camelCase）／**パス設定**（ベースパスからの相対パス）／メソッド／処理内容。フルパス＝ベースパス＋パス設定。
  - **入力仕様**：No / 論理名 / 物理名 / 型（型参照は `※型定義書【...】を参照`）。
  - **入力チェック（実行順）**：No(自動採番) / 論理名 / 共通チェック仕様名（定義）・個別チェック内容。共通仕様は `【入力値チェック システム共通仕様書】` を参照。
  - **出力仕様**：No(自動採番) / 論理名 / 物理名 / 型。
  - **処理フロー**：No(自動採番) / 概要 / 内容。

## 固有の決定事項
- **処理フローは「入力値チェック → サービスへ委譲 → 応答」**を基本とする。業務ロジック（条件組立・絞り込み・ドメイン変換）はサービスに置き、本書で重複詳細化しない（`【...Service】の<メソッド>に委譲` と記す）。
- コントローラーは状態を保持しない（ステートレス）。
- **横断参照データ（名称等のマスタ取得）API はリソース指向**：複数機能から使う名称・マスタ取得は、機能単位ではなく**対象マスタ種別ごと**にエンドポイントを定義する（過剰取得・ページ単位の増殖を避ける）。機能グループは対象マスタの所属とし、特定の参照元には紐付けない。詳細は [00_共通規範.md](00_共通規範.md)「レイヤ責務・設計方針」を参照。
