# 実装計画立案スキル

本スキルでは **コードを実装する前の計画立案** の方法論・手順を定める。
docgen-plan が詳細設計の作成計画を立てるのと対をなし、本スキルは **完成済みの詳細設計を正本としたコード実装の計画**を立てる。

## スキルの前提

スキルの仕様には以下の前提を置く。前提を満たしていない場合はユーザーにその旨を告知し、指示を仰ぐ。

- 完成済みの基本設計書・詳細設計書がリポジトリ内に存在すること
- 実装規約（コーディング規約・実装共通規範）が定められていること
- プロジェクトのビルド・テスト・フォーマッタ・リンタが定義されていること

### スキル使用時のルール

- **設計書（基本設計・詳細設計・実装規約）の編集は禁止**されている。
  - それらの中で誤り・矛盾を見つけた場合は、自己判断で実装に進まず、ユーザーに対応（docgen 系での修正等）を促す。
- 本スキルでは **コードの実装は行わない**。あくまで計画の立案までを担い、実装は codegen-exec が担う。
- 作業中にこのスキルやプロジェクト全体での指示で明確に定められていない事象に遭遇した場合は、自己判断せずユーザーに判断を仰ぐ。

## 計画の目的

実装の着手にあたり、システム全体を俯瞰した上で、該当機能の実装に必要な要素（実装対象・依存・既存実装の再利用・必要なテスト）を事前に洗い出し、作業の概要と着手順を明らかにする。

## 中間生成物の配置場所の作成

本スキルおよび codegen 系スキル(codegen-exec / codegen-check)が共有する中間生成物は、
**リポジトリルート直下の `.codegen/` 配下**に配置する。対象が存在しない場合はこれを作成する。
また `.codegen/` には `.gitignore` を配置し、配下のファイルはリポジトリ管理対象とされないようにする。

- `.codegen/plan/` … 実装計画
- `.codegen/progress.md` … 進捗・決定台帳（本スキルが初期化し、codegen-exec が工程ごとに更新する）
- `.codegen/sources.lock.json` … 各実装が依拠した設計書の {相対パス, role（primary=詳細設計 / supplement=基本設計）, sha256} の記録。**`doctool hash` が機械生成し手編集しない**（codegen-exec が工程完了時に記録）。設計変更を検出するベースライン。

## 作業手順

### 1. 既存の成果物の確認

既存の成果物がある場合、gitignore の設定を除き削除した上で以降の内容を再度実施して最新化する。
ただし `.codegen/progress.md`（進捗・決定台帳）を再生成する場合は、**既存の「決定ログ」「申し送り」を引き継ぐかをユーザーに確認**する（過去の横断的決定が失われると後続工程の設計ドリフト・手戻りを招くため）。

### 2. 詳細設計（正本）の読み取りと変更検出

リポジトリ内を探索して詳細設計書・基本設計書を配置しているディレクトリを明らかにする。見当たらない場合はユーザーに尋ねる。`_old` や `bak` などのディレクトリ配下または zip ファイルにある旧バージョンは対象外とする。

- **設計書は読む時に doctool を経由して最新化する**（事前一括変換はしない）。バイナリ（docx/xlsx）は `doctool cache <src>`（未変更ならスキップ＝安価）を通してから、出力された `.doctool-cache/<相対パス>.md` を読む。**`.doctool-cache/` の .md を doctool を通さず直接読まない**（最新性を担保するため）。md／テキストは複製せず**原本を直接読む**。
- **着手時の変更検出（reconciliation）**：`.codegen/sources.lock.json` に対象の記録があれば、記録された各設計書の指紋を、同 lock に対する `doctool status --lock`（changed/missing があれば変更あり・終了コード1）で突き合わせる。差分があれば「上流変更あり」を確定し、影響する実装・テストを洗い出して**再点検の対象として計画に組み込む**（primary=詳細設計の変更は再実装の要否を確認、supplement=基本設計の変更は影響確認）。検出は自動・**是正は承認制**。設計書の誤り・矛盾は自己判断で実装に進まず docgen 系での修正を促す。

### 3. 既存実装・実装規約の調査

システム全体のコードと実装規約を調査し、実装の体系・確立済みのパターンを理解する。

- ビルド構成・依存ライブラリ・フレームワーク（例: Spring Boot / Gradle）
- 実装規約の正本から、横断的に適用される規範・共通部品の所在を棚卸しする。所在が不明な場合はユーザーに確認する。
- 既存実装で確立しているレイヤ構成・パッケージ構成・命名規約・テストの書き方を、実例（ファイルパス）とともに把握する
- フォーマッタ・リンタ・テストの実行コマンド（例: `gradlew build` / `test` / `spotlessApply` / `checkstyle`）

### 4. 全体レベルの実装計画立案

調査結果をまとめ `.codegen/plan/全体計画.md` に出力する。

- プロジェクトの名称や達成したい目的
- アーキテクチャ層構成と各層の責務（例: コントローラー / サービス / データアクセス / 型・テーブル）
- 機能間で共有される要素（型・共通部品・テーブルアクセス等）と、それらの再利用方針
- 実装すべき機能の一覧およびそれらのグループ関係
- 共通の実装規約・命名規約の要点（実装規約の正本への参照と、本プロジェクトで確定済みの方針）

### 5. 個別機能レベルの実装計画立案

全体レベルで明らかになった機能一覧に対して、機能ごとに以下を調査してまとめ `.codegen/plan/機能別計画_<機能名>.md` に出力する。

- 依存する機能・共通部品の有無および対象の一覧
- インプットとする詳細設計書（定義書単位で列挙。実装の正本）
- アウトプットとする実装（実装対象のクラス／ファイルと出力先パス、対応するテスト）
- 既存実装の有無と再利用・変更方針
  - 既存実装に修正を加える場合は、修正によって発生する影響範囲を明確にする
  - 設計と矛盾しない限り、既存実装の構造を大きく変えることは避ける
- 必要なテストの観点（正常系・境界値・異常系の概略）

### 6. 着手順の決定と全体計画への追記

個別機能の依存関係から、推奨される実装着手順を導く。`.codegen/plan/全体計画.md` に以下を追記する。

- 各機能・各定義書単位の工程に分解した、推奨される着手順
  - 工程の単位は **詳細設計の定義書単位**（型情報定義書・テーブル定義書・データアクセス定義書・イベント定義書 等）とし、依存の下流（共有要素）から積み上げる順とする。

### 6.5 進捗台帳の初期化

実装の進捗と横断的決定を一元管理する台帳 `.codegen/progress.md` を生成する。
codegen-exec が着手時に参照し（次の未着手工程の特定・決定の踏襲）、工程完了ごとに更新する。

- **工程進捗**: §6 で定めた着手順の各工程を、`- [ ] 工程N <概要（定義書単位）>` の未着手チェックボックスとして列挙する。
- **決定ログ**: 横断的に効く確定事項（命名規約・共通部品の切り出し・パッケージ配置・型方針・テスト方針 等）を記録するセクションを用意する（codegen-exec が工程ごとに追記）。
- **成果物の所在 / 技術メモ / 申し送り**: それぞれ空セクションを用意する。

> この台帳は中間生成物であり `.codegen/` 配下（リポジトリ管理対象外）に置く。

### 7. 出力の検証

出力した成果物に対して再度全体を俯瞰し、実装計画にシステム設計との矛盾や抜けがないか確認する。
結果についてユーザーにレポートし、内容の承認を得る。
このプランの実行後、コード実装に入る前にチャットのコンテキストを切り落とすようユーザーに推奨する。
