# このドキュメントについて

> **詳細設計書の生成結果を自己レビューする際の規約と作業手順**を定める。

## このスキルについて

製造済みの詳細設計書について記述内容が基本設計書および先行する実装との矛盾がないことを確認する
以下にこのスキルの動作プロセスを記載する。

### 1. 詳細設計書・基本設計書の読み取りと変更検出

リポジトリ内を探索して詳細設計書・基本設計書を配置しているディレクトリを明らかにする。見当たらない場合はユーザーに尋ねる。`_old`や`bak`などのディレクトリ配下またはzipファイルにある旧バージョンは対象外とする。

- **設計書は読む時に doctool を経由して最新化して読む**。バイナリ（docx/xlsx）は `doctool cache <src>`（未変更ならスキップ）を通してから `.doctool-cache/<相対パス>.md` を読む。**`.doctool-cache/` の .md を doctool を通さず直接読まない**（最新性を担保するため）。md／テキストは原本を直接読む（ドキュメントから参照される画像等のバイナリは読む時に必要なら複製する）。
- **上流変更の検出**：`.docgen/sources.lock.json` に対象の記録があれば、記録された基本設計の指紋を、同 lock に対する `doctool status --lock`（changed/missing があれば変更あり・終了コード1）で突き合わせ、詳細設計を作った後に基本設計が変わっていれば「詳細設計が依拠した基本設計から上流が変わっている（再点検要）」を検出事項として報告する（是正は docgen-exec／人手であり本スキルでは修正しない）。


## 2. レビューの実施

詳細設計書の内容について、次の観点の下でレビューを実施する。

### 観点

- **基本設計と矛盾しないこと**
- **設計の過不足がないこと**
- **既存の詳細設計と整合すること**：
    - 作成した詳細設計の参照先と処理が矛盾せず整合していること。
    - 個別定義書とそれを束ねる一覧表（索引）が 1:1 で対応すること。
    - 同様の機能と記述の粒度が揃っていること。
- **規約違反がないこと**：プロジェクト内で規約や書式が定められている場合、作成した成果物
がそれらに反していないこと。
- **一意な実装が可能であること**：表現に曖昧さがなく、詳細設計書を読んだ人が誰でも同じ実装が可能であること。
- **依存関係のチェック**: 成果物は下流の工程の成果物や、中間成果物(進捗台帳や機能別計画など)を参照していないこと。

#### 名称の観点

- **名称の自己整合**：成果物のファイル名・ヘッダー・本文で同一対象を指す表記は、互いに食い違わない。
- すべての物理名（型・プロパティ・クラス・メソッド・テーブル/列/制約・エンドポイント等）が命名規則に適合する識別子であること。
- 物理名欄に論理名・説明・値域などの自然言語を書いていないこと

#### 表の観点

- **冗長記述の排除**：各列について、列見出し・他列・統制語彙が既に担う情報をセル本文で重複していないこと。重複があれば項目固有の差分のみ残す。
- **採番の表ごと独立**：自動採番のNo列が、表ごとに1始まりで振り直されていること（表をまたいで連番が継続＝地続きになっていないこと）。地続きがあれば `doctool normalize` で是正する。

## 3. レビュー結果の報告

レビューした結果を`.docgen/progress.md`(進捗台帳)に記載する。該当ファイルが存在しないは作成する。
記録後、ユーザーにレビュー結果を報告する。
合わせて、ユーザーにはレビュー結果以外の指摘事項がないかを尋ねる。
ユーザーから追加の指摘事項やレビュー内容への指摘があった場合は都度進捗台帳に記載する。
