# testgen 共有規範

本スキルは testgen ファミリの各スキルが従う規範の正本である。タスクの手順は各スキル
(testgen-plan / testgen-exec / testgen-check)が担い、本スキルは手順が依存する規範のみを定める。

- 本規範に記載が無く判断できない事項はユーザーに確認する。
- 規範の改訂は過去のテスト実施単位へ**遡及適用しない**。過去の実施単位はその時点の
  実施記録(不具合検出に至った証跡を含む)として扱う。

## 目的と範囲(既定の立場)

- E2Eテストは**品質を保証する主体**として設計する。システムの振舞いについて、設計書との
  乖離がないかを**網羅的に**検証し、品質を担保する。
  - 単体/結合テストは回帰テストとしての利用が主目的であり、それにより品質が保証されたとは
    みなさない。
  - 正しくテストした結果発見された失敗は、コードの品質向上につながるものであり歓迎される。
  - **設計と実装の乖離の扱い**: 乖離を発見しても、期待結果を実装側へ寄せない・是正方向の
    確認を取らない。テストは設計どおりに実装し、乖離は**テストの失敗として検出**する。
    失敗の報告には「設計と実装が一致していないための失敗」である旨を、設計の文言(出典付き)と
    実測値の対で記す。是正(実装修正か設計修正か)の判断は検出後にユーザーが行う。
    設計文書**同士**の食い違い・設計の欠落はこの対象ではなく、文書正本規範に従い報告・確認する。
  - テストは「実施した」だけでは足りず、**操作と結果の正しさを人が証跡から追跡・確認できる**
    ことをもって完了とする。
- E2E の守備範囲は、実ブラウザ・クライアントJS・実レンダリング・画面遷移・複数画面フロー・
  人の受け入れ。JUnit(単体・スライス・結合)とのテスト重複は禁じない。
- 以上は本スイートの既定の立場である。プロジェクトが異なるテスト戦略を明示する場合
  (後述の「テスト規約」ロール文書)はそちらが優先する。

## 規範の索引

| 規範 | 内容 | 主な参照者 |
| --- | --- | --- |
| `references/文書正本規範.md` | 設計文書・様式のロール定義と探索、正本の優先順位、食い違い時の扱い | plan(導出全般)、exec / check(期待結果・様式の解釈) |
| `references/実施単位・配置規範.md` | 実施単位の運用、流用複製、成果物配置の既定、VCS 整備 | plan / exec / check |
| `references/証跡規範.md` | 証跡の有効性基準(フレーム規格・代理証跡・機械検証・証跡ログ) | exec(生成)、check(検分)、plan(期待結果の表現) |
| `references/実行ハーネス規範.md` | キットの前提条件、実行プロファイル・タスク、検証部品、ツール | exec、check |
| `references/到達手段カタログ.md` | 到達不能に見える設計分岐への公認到達手段（バイパス・別セッション・セッション失効・障害シーム等）と対象外判断の照合手順 | plan（対象外判断の関所）、exec（手段の実装） |
| `references/テストデータ規範.md` | データ・期待値の参照可能性、シードID帯域、1画面原則 | plan、exec |

各スキルは自分の作業に関わる規範を読み込んでから作業する。

## プロジェクトによる上書き

プロジェクト側に「テスト規約」ロールの文書(発見方法は文書正本規範)が存在する場合、
配置・様式・環境・戦略などプロジェクト固有の決定はそちらが本規範の既定を上書きする。
ただし**正本の扱い(文書正本規範)と矛盾する定めを見つけた場合は、黙って従わず
ユーザーに確認する**。

## 保守・可搬性の規律

本スイート(スキル文書・ハーネスキット・同梱ツール)を更新する際は、以下を守る。
違反はスイートを特定プロジェクトでしか使えなくする欠陥として扱う。

1. スキル文書・キットのコードに、プロジェクト固有の識別子(リポジトリ内の実パス・組織名・
   ベースパッケージ・機能名・画面名)を書かない。プロジェクトの文書は**文書ロール経由**で、
   プロジェクトのコードは**糊クラス(exec が転写時に生成)経由**でのみ参照する。
2. スイート自身の成果物の配置・定数は「**既定値+プロジェクト側で上書き可**」の形でのみ
   記述する。既定値の直書きを複数箇所に増やさない(正本は一箇所、他は参照)。
3. ハーネスキットは中立パッケージを維持し、アプリ側クラスの import を追加しない。
   アプリ依存が必要になったら糊クラスへ隔離する。
4. 転写済みプロジェクト側(`src/test`)で加えた改良をキットへ還元するときも、1〜3 の分離を
   通してから持ち込む。
5. スキル・キットの更新後は、スキル配下にプロジェクト固有識別子が混入していないことを
   確認してから完了とする(例: 作業中のリポジトリの組織名・ベースパッケージ・ドキュメント
   実パスでスキル配下を検索し、ヒット 0 を確認する)。
